# Orca 資安評估

> 對象：[stablyai/orca](https://github.com/stablyai/orca)（MIT License，著作權標註 Lovecast Inc.）
> 起因：[20260813.md](20260813.md)「GitHub趨勢｜Orca平行coding agent orchestrator」該則新聞建議評估，導入前先做資安查核
> 評估日期：2026-08-13　評估版本：commit `c61f29639c86`（2026-08-12）
> 方法：shallow clone 原始碼實際檢視手機遠端操控機制、憑證儲存、worktree隔離，非僅閱讀README

## 結論

Orca 是一個很成熟的 Electron IDE（monorepo ~1.3萬檔案、5097個測試檔、23個CI workflow），手機遠端操控走的是自建 relay 服務（`onorca.dev`），但傳輸內容全程 E2EE（Curve25519/XSalsa20-Poly1305，relay 只轉發密文看不到明文）、host 端還有一套嚴謹的 challenge-response 身分證明協定；憑證儲存也確實用 OS 原生機制（iOS/Android Keychain、Electron `safeStorage`、macOS Keychain）。真正的風險核心不在手機遠端操控的加密機制（做得不差），而在於：(1) Orca 本身**明文承認**不做 worktree 之間的安全沙箱隔離（"runs trusted Orca code with the same user identity"），30+ 個 coding agent 全部以同一個 OS 使用者身分平行執行，彼此可互相存取檔案系統與憑證；(2) 各 coding agent（Claude Code/Codex/Gemini/Aider等）本身的執行核准模式（是否要求人工確認每個指令）是那些 CLI 工具自己的邏輯，Orca 只是終端機包裝層，並不統一強制核准——若使用者用 `--dangerously-skip-permissions` 之類旗標啟動底層 agent，手機下的指令一樣會無人工確認直接執行。建議結論：**可在獨立測試機／隔離帳號上，由 1-2 位工程主管試裝評估手機遠端操控與 worktree 並行體驗，暫不建議在含生產機敏資料或客戶資料的工作機上啟用手機遠端連線**，尤其要先確認每個平行執行的 coding agent 都設定為需要人工核准模式,再談導入。

## 一、查證通過的項目

| 項目 | 查證結果 |
|---|---|
| 手機端到桌面端傳輸加密 | `mobile/src/transport/e2ee.ts` 使用 tweetnacl 做 Curve25519 ECDH（`nacl.box`）+ XSalsa20-Poly1305 認證加密，JSON RPC 走 `base64([24-byte nonce][ciphertext])`；relay 僅轉發密文，見 relay 端 `src/main/runtime/relay/relay-host-proof.ts` 的 host proof 驗證邏輯只處理已加密的 transcript |
| Host 身分驗證（防relay/攻擊者偽造host） | `src/main/runtime/relay/relay-host-proof.ts` 實作 challenge-response 協定：relay 送出以 host 公鑰加密的 challenge，host 需解密並回傳綁定 `userId`/`profileId`/`organizationId`/`relayHostId`/`assignmentEpoch` 等16個欄位的 HMAC-SHA256 簽章，且所有比對均用 `timingSafeEqual`（防時序攻擊），10秒挑戰窗+30秒NTP容差 |
| 手機端憑證儲存 | `mobile/src/transport/pairing-keychain.ts` 用 `expo-secure-store`（`WHEN_UNLOCKED_THIS_DEVICE_ONLY`，即iOS Keychain/Android Keystore，明確排除iCloud備份同步）；relay device token / resume token 走 `mobile-relay-credential-bundle.ts`，強制要求 native secret store（web平台直接丟例外拒絕儲存） |
| 桌面端敏感設定加密 | `src/main/protected-secret-persistence.ts` 使用 Electron `safeStorage`（底層為macOS Keychain/Windows DPAPI/Linux libsecret）加密如 `opencodeSessionCookie`、`httpProxyUrl` 等敏感欄位，加密不可用時會降級（不明文外洩，只是保留舊密文） |
| Claude Code 憑證（macOS） | `src/main/claude-accounts/keychain.ts` 透過 `security` CLI 讀寫 macOS 原生 Keychain（`Claude Code-credentials` service），非明文檔案；Windows/Linux 對應函式明確 no-op 回傳null，代表這兩個平台上 Orca 不介入、由 Claude Code 自己的既有機制管理 |
| Pairing 配對流程需實體接觸 | `mobile/src/transport/pairing.ts` 走 `orca://pair?code=...` 深連結或QR碼／貼上base64碼，須由桌面端主動產生配對碼並經由QR掃描/複製傳給手機，非攻擊者可遠端無中生有觸發 |
| 遙測（telemetry） | `src/renderer/src/lib/telemetry.ts`：renderer 完全不含 PostHog SDK（唯一client在main process），有明確 `TelemetryConsentState`（`enabled`/`pending_banner`/`disabled` + `do_not_track`/`orca_disabled`/`ci`/`user_opt_out`原因)，首次啟動有同意橫幅，隱私說明公開於 `https://www.onorca.dev/docs/telemetry` |
| 安裝雜湊驗證（macOS Homebrew） | `Casks/orca.rb` 有 arm64/intel 各自的 SHA256 雜湊值 pin 住對應版本下載檔 |
| 程式碼簽章/公證 | macOS 走 Apple Developer ID codesign + notarize（`hardenedRuntime`/`notarize` 皆綁 `isMacRelease`）；Windows 走 SignPath Foundation 簽章（`config/electron-builder.config.cjs` `signtoolOptions.publisherName`） |
| CI／測試覆蓋 | `.github/workflows/` 有 pr.yml（lint+型別感知程式碼品質稽核）、e2e.yml、mobile.yml、win-crash-survival-e2e.yml、windows-signing-rehearsal.yml 等25個workflow；原始碼庫內含 5097 個 `*.test.ts(x)` 檔案 |
| 依賴套件精簡 | `package.json` production dependencies 僅23個，均為知名套件（tweetnacl、ws、zod、ssh2、node-pty、electron-updater等），無明顯來路不明的套件 |
| 安全測試意識 | `examples/` 目錄明確保留 `hostile-panel`（對抗性插件fixture，供 containment 測試使用），`electron-builder.config.cjs` 註解特別強調此目錄「must never reach a user's install」 |

## 二、風險項目

### 高：worktree／agent 之間無安全沙箱隔離，credential 與檔案系統對所有平行 agent 共享

`docs/ai-vault-process-isolation-plan.md` 的「Non-goals」段落原文明講：「Treating the service process as a security sandbox. It runs trusted Orca code with the same user identity.」（不把這個服務程序當作安全沙箱，它以與使用者相同的身分執行受信任的Orca程式碼）。這代表 Orca 讓 30+ 個 coding agent 在不同 git worktree 中「平行工作」時，隔離僅止於 git 檔案樹（每個 worktree 有獨立的工作目錄），但所有 agent 進程都是同一個 OS 使用者身分、共享同一個 `$HOME`、同一份環境變數、同一個 Keychain 存取權——`src/main/providers/local-pty-provider.ts` 顯示 agent 是以本機 PTY 進程方式啟動並繼承 process 環境，並無容器化或個別使用者隔離。實務意涵：若其中一個 worktree 因prompt injection（例如被注入的第三方repo內容）導致某個 coding agent 被誘導執行惡意指令，該指令能存取的範圍是**整台機器**（其他worktree的原始碼、`~/.claude`/`~/.codex`等其他agent的session與憑證檔、瀏覽器cookie等），而不僅限於自己的worktree。這是「30+個agent平行跑」這個賣點本身帶來的攻擊面放大，並非Orca特有的缺陷（任何本機多進程agent orchestrator都有此問題），但官方文件自己承認「非安全邊界」，代表使用者不能誤以為worktree=沙箱。

### 高：手機遠端操控的下指令權限，實際由底層 coding agent 自己的核准模式決定，Orca 不做統一強制

Orca 本身是終端機/IDE殼層，不是自帶agent邏輯的產品（不像T3 Code是自研agent runtime）。手機App透過E2EE通道送出的「指令」，最終效果等同於在該桌面worktree的終端機視窗打字/貼上文字給正在跑的 Claude Code / Codex / Gemini CLI 等程序——這些底層CLI各自有自己的權限核准邏輯（例如Claude Code的permission prompt、或使用者自行加上`--dangerously-skip-permissions`之類旗標繞過核准）。**未能在Orca原始碼中找到**任何統一攔截並強制要求人工核准的機制（搜尋 `yolo`/`auto-approve`/`bypassPermissions`/`permission-mode`等關鍵字在`src/`下無相關命中）。也就是說：如果同仁圖方便把底層agent設成免核准模式，手機遠端配對成功後，攻擊者（或被盜手機）即可透過已配對的裝置對公司機器下達等同無人值守執行的指令，風險核心其實轉嫁到「底層每個coding agent各自的啟動旗標」而非Orca本身的可控範圍。

### 中：relay 服務為 Stably 自建中繼（onorca.dev），非point-to-point直連時仍依賴第三方基礎設施

`src/main/runtime/relay/relay-control-url.ts`、`relay-host-proof.ts`等程式碼與測試（`onorca.dev`關鍵字命中55個檔案，含`c2.relay.onorca.dev`測試fixture)確認 Orca 在無法直連（NAT/防火牆環境）時會透過 Stably 營運的relay服務轉發加密流量。雖然內容經E2EE保護、relay理論上看不到明文（`decryptBytes`失敗時回傳null，relay無法解密），且host proof協定要求host端持有私鑰才能通過relay的身分挑戰，但：(1) relay服務仍掌握連線metadata（何時連線、host/使用者/組織ID等——`relay-host-proof.ts`的transcript欄位就包含`userId`/`organizationId`）；(2) relay可用性/可靠性完全依賴Stably維運，`docs/mobile-relay-ux-findings.md`本身也記錄多起relay連線狀態機bug（雖為UX層問題非安全漏洞，但反映relay路徑複雜度高，值得留意其成熟度）。**未能驗證**relay伺服器端（非本repo，屬Stably私有後端）的實際部署與資料保留政策。

### 中：SECURITY.md 缺失，無公開弱點回報管道

repo根目錄**未找到**`SECURITY.md`，GitHub亦無法從原始碼中確認是否有正式的security policy、safe-harbor條款或漏洞回報信箱（相較於同類專案T3 Code有`security-policy.astro`頁面與`security@ping.gg`信箱）。若企業內部發現漏洞，目前**未能驗證**官方是否有對應窗口與SLA。

### 低：安裝雜湊驗證僅涵蓋macOS Homebrew，Windows/Linux依賴簽章鏈非雜湊pin

`Casks/orca.rb`對macOS的DMG有SHA256 pin，但Windows（nsis/SignPath）與Linux（AppImage/deb/rpm）走的是code signing（信任簽章者身分）而非使用者可自行比對的公開雜湊清單；`.github/workflows/`中**未查到**額外的cosign/sigstore/SLSA provenance機制。這比單純curl|bash安裝安全（有簽章鏈把關），但企業若要做離線雜湊校驗，目前只有macOS管道方便執行。

### 低：Lovecast Inc. 與 Stably AI 品牌不一致

`LICENSE`著作權標註「Lovecast Inc.」，但README/package.json/GitHub組織均為`stablyai`。此為常見「營運品牌 vs. 登記法人」的落差（新創常見），非技術風險，但建議簽約/採購前向官方確認法律實體對應關係，以利日後條款/責任歸屬釐清。

### 低：依賴套件抽查

`package.json` production dependencies 僅23個常見套件，devDependencies 100個。抽查未發現已知高風險套件版本，但**未能驗證**完整相依樹（pnpm-lock.yaml的間接依賴)是否含CVE，僅為抽查非完整SCA掃描。

## 三、建議的安裝與使用方式

1. 先在**與公司網域、VPN、生產機敏資料隔離**的獨立測試機或一次性帳號上安裝試用，不接上任何含客戶資料或機敏原始碼的正式worktree。
2. 手機遠端操控功能**先不開啟**，待確認relay連線metadata的保留政策與貴司資安要求相容後再評估開啟；若開啟，優先使用同一區網下的直連模式（減少對onorca.dev relay的依賴）。
3. **強制**每個平行執行的coding agent（Claude Code/Codex/Gemini等）都設定為需要人工核准每一步操作的模式，不要為了方便使用免核准/YOLO模式——這是本評估認定的最高風險項，且是Orca無法代為把關的部分。
4. macOS安裝優先透過Homebrew Cask（有SHA256雜湊pin），Windows/Linux安裝檔下載後確認數位簽章有效（SignPath/相應憑證鏈)。
5. 關閉或確認遙測同意狀態，依`https://www.onorca.dev/docs/telemetry`確認實際回傳欄位是否符合貴司資料外流規範。
6. 試裝期間限定1-2位工程主管/資安人員，在可拋棄的repo/worktree中操作，實測worktree之間是否真的能互相讀到彼此的憑證檔案（例如故意在worktree A的agent嘗試讀取`~/.claude`下屬於另一個帳號/session的資料，驗證本報告「無沙箱隔離」的結論）。
7. 向官方詢問是否有SECURITY.md/漏洞回報管道之外的正式資安文件，並確認relay服務（`onorca.dev`）的資料保留與存取記錄政策。

## 四、PoC 的環境要求

- 獨立測試機或VM（非公司網域加入、非生產環境），macOS/Windows/Linux桌面版皆可，macOS優先（有雜湊pin且是官方主要開發平台）。
- 至少兩個獨立git worktree、兩個不同的coding agent帳號（例如兩組不同的Claude Code登入），用以實測worktree/憑證隔離是否確實。
- 一支測試用手機（iOS TestFlight或Android APK）用於驗證QR配對、E2EE連線建立、relay/直連切換行為。
- 全程觀察配對過程中生成的憑證檔案位置與加密狀態（`~/.orca`、Electron userData目錄、手機端Keychain項目)，確認本報告列出的儲存機制與實際行為一致。
- 若要測試relay路徑，需準備NAT後方的桌面環境以強制觸發relay轉發（而非直連），並用網路封包擷取工具確認relay轉發內容確實為密文。

## 五、給決策者的一句話

Orca的手機遠端操控與憑證儲存機制本身做得比預期紮實（E2EE、host身分挑戰、OS原生金鑰庫），但它讓30+個agent以同一個系統使用者身分平行跑、官方文件自己承認「不是安全沙箱」，真正該卡關的是「有沒有強制每個底層agent都開人工核准模式」，而不是懷疑加密夠不夠。
