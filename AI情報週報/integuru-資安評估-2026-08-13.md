# Integuru 資安評估

> 對象：[Integuru-AI/Integuru](https://github.com/Integuru-AI/Integuru)（License：AGPL-3.0）
> 起因：[20260813.md](20260813.md)「GitHub趨勢｜Integuru逆向工程私有API」該則新聞已提醒法遵風險，這裡專注技術面資安查核
> 評估日期：2026-08-13　評估版本：`b063940`（"Update README for current Integuru site (#70)"，2026-05-26）
> 方法：shallow clone 原始碼實際檢視HAR/cookie資料在LLM分析流程中的處理方式，非僅閱讀README。注意：README已明確聲明此repo為「Integuru v0」，目前產品已搬到 www.integuru.com 閉源版本，本評估僅適用於此公開v0原始碼。

## 結論

**這套工具的設計前提就是要處理使用者的完整session憑證等級敏感資料**：`create_har.py`會啟動Playwright瀏覽器，要求使用者親自登入目標網站（含完成2FA），然後把整個瀏覽器session的HAR網路日誌（`network_requests.har`，`record_har_content="embed"`會把回應內容原封不動嵌入）與Cookie（`cookies.json`，明文JSON，含`value`欄位）存到執行目錄下的明文檔案，之後整份丟給雲端LLM（OpenAI GPT-4o／o1-preview）分析並生成程式碼。

實際讀碼後，Cookie**標頭本身**（HTTP `Cookie:` header）在送進LLM前確實有被程式過濾掉（見下方查證），這是本評估唯一可驗證的正面控制。但這個過濾**僅止於Cookie標頭**，範圍很窄：HTTP回應內文（可能含帳號餘額、access_token、個資）、URL query string、POST body中的session token/API key，全部逐字送進OpenAI的prompt，沒有任何遮罩或紅線清單。換言之，「Cookie header不外流」是真的，但「敏感資料不外流」是假的——只要一組token同時出現在URL或body裡（很常見的模式），一樣會被送給OpenAI。

**建議結論：這是一個技術上可行、但資安治理近乎空白的實驗性PoC（作者自稱"v0"），不建議在任何真實帳號、真實金融或含PII的網站上直接使用；若要用，必須自建遮罩層並在隔離環境執行，且應優先評估目標網站ToS是否禁止此類行為。**

## 一、查證通過的項目

1. **Cookie HTTP標頭在送給LLM前確實被過濾**
   - `integuru/util/har_processing.py` 第15–39行 `excluded_header_keywords` 明確列出 `"cookie"`，並在 `format_request()`（第48–53行）建構要送進LLM分析的 `Request.headers` 時，用 `if not any(keyword.lower() in header.get("name","").lower() for keyword in excluded_header_keywords)` 排除含cookie的標頭。
   - `integuru/models/request.py` 第42–51行 `to_minified_curl_command()` 額外註明「Minifies the curl command by removing referer and cookie headers. This is done to reduce LLM hallucinations.」（原始動機是防止幻覺，非資安考量，但客觀上有效果）。
   - `integuru/agent.py` 第194–196行，識別動態部分的prompt中也明文指示LLM「IGNORE THE COOKIE HEADER」。

2. **HAR/cookie檔案不會被意外commit進git**
   - `.gitignore` 第155–156行有全域 `*.har` 與 `*.json`（連同 `*.png`），會涵蓋預設檔名 `network_requests.har`、`cookies.json`、`dag_visualization.png`。這是**巧合式的保護**（`*.json`是為了忽略各種暫存json，不是專門為cookie設計），但實際效果正確。
   - `.env`（OpenAI API key存放處）也在 `.gitignore` 第116行被忽略。

3. **LLM訓練聲明**：README「Privacy Policy」章節（第131–140行）聲明「Collected data is stored locally」「The LLM is not trained or improved by the usage of this tool」——但這是**未經第三方稽核的自我聲明**，且此聲明僅適用OpenAI API（依OpenAI API資料使用政策，非ChatGPT網頁版，API預設不用於訓練），無法從原始碼驗證是否確實遵守。

4. **有基本CI**：`.github/workflows/ci.yml` 跑 `pytest`；`tests/test_integration_agent.py` 只是mock測試三個agent函式，覆蓋率很低，不含任何資安相關測試。

5. **Dependabot已啟用**：`.github/dependabot.yml` 對 `pip` 與 `github-actions` 做每週依賴更新掃描，屬於基本衛生但非資安審查。

## 二、風險項目

### 高：Cookie/Session Token本體以及原始HTTP回應內容，仍會被送給OpenAI做分析

雖然Cookie**標頭**被過濾（見上方「查證通過」），但整條資料管線中至少四處會把敏感值原封不動送進OpenAI prompt：

- **`integuru/agent.py` `end_url_identify_agent()`**（第57–62行）：把 `self.har_urls`（每個HAR請求的method/url/回應格式/回應前30字，來自`har_processing.get_har_urls()`）整包塞進prompt送給GPT-4o，用來判斷哪個URL負責目標動作。URL本身常帶有 `accountId=123&token=xxx` 這類敏感query string，未做任何遮罩，唯一的過濾只有 `excluded_keywords = ("google","taboola","datadog","sentry")` 這種第三方追蹤網域黑名單（第7–13行），與敏感度無關。
- **`integuru/agent.py` `dynamic_part_identifying_agent()`**（第146–225行）：送出 `to_minified_curl_command()` 的結果——雖然移除了Cookie/Referer標頭，但URL、query string、request body（可能含session token、bearer token、API key）完全原樣送出。
- **`integuru/util/print.py` `generate_code()`**（第138–266行）：程式碼生成階段會把**完整HTTP回應內文**（`response_text`，第176、206行的prompt）逐字塞進prompt送給o1-preview（若回應是JSON或<100,000字元的HTML）。回應內文常見帳號資訊、餘額、個資、甚至內嵌的`access_token`欄位，這裡沒有任何脫敏處理。
- **`integuru/util/print.py` `aggregate_functions()`**（第268–314行）：把整份 `generated_code.txt` 內容送給OpenAI做函式整併——但這步驟執行時機在 `swap_string_using_obfuscation_map()`（見下方風險項）之後，所以理論上這一步的動態值已被混淆，屬於較安全的一步。

**結論：宣稱移除的只有Cookie標頭，Cookie的「值」（session token）若同時出現在URL/body中，或任何其他形式的認證憑證（bearer token、API key、access_token），都會被明文送進OpenAI。** 這正是README自己在Privacy Policy段落沒有講清楚、但README中「## Note on 2FA」一段（第112–114行）反而要求使用者「obtain the cookies/auth tokens/session tokens after 2FA. These tokens will be used in the workflow」——用詞上已默認token會進入處理流程，卻沒說明會被送去LLM。

### 高：本機明文儲存高敏感憑證，無加密、無存取控制、無過期機制

- `create_har.py` 第27–28行：`cookies.json` 用 `json.dump(cookies, f, indent=4)` 明文寫入當前工作目錄，每筆cookie含 `name`/`value`/`domain`/`path`/`httpOnly`/`secure`/`sameSite`（見 `integuru/util/har_processing.py` 第216–242行 `parse_cookie_file_to_dict()` 的解析欄位），也就是完整session/認證cookie的明文值。
- `network_requests.har` 由Playwright `record_har_content="embed"` 產生（`create_har.py` 第12行），會把每個請求/回應的**內容本體**（含JSON回應內文）都嵌入HAR檔案，同樣是明文。
- 兩個檔案存在使用者本機執行目錄，沒有加密、沒有存取權限限制、也沒有使用後自動清除機制。任何能存取該機器/該目錄的人（或惡意套件、其他程式）都能直接讀走整組session憑證去冒充該使用者登入。
- `.gitignore`的保護只防止「意外commit進git repo」，不保護「本機磁碟外洩」（例如透過其他惡意軟體、雲端同步資料夾如Dropbox/OneDrive自動上傳，若專案資料夾剛好在同步路徑內）。

### 中：生成的Python程式碼——中繼過程含明文cookie值，最終檔案理論上有混淆但依賴實作正確性

- `integuru/util/print.py` `generate_code()` 第145–148行，對 `node_type == "cookie"` 的節點會直接產出這行程式碼字串（不經過LLM）：
  ```python
  return f"{cookie_value} = cookie_dict['{cookie_key}']"
  ```
  這裡的 `cookie_value` 是實際的cookie明文值（來自 `graph_builder.py` 第302–322行 `find_curl_from_content()` 比對出的 `search_string`，即真實token字串），被當成**Python變數名稱**直接寫入尚未混淆的中繼碼字串中。
- 之後 `print_dag_in_reverse()`（`print.py` 第339–451行）會呼叫 `generate_obfuscation_map()` 與 `swap_string_using_obfuscation_map()`（第316–337行），把所有出現在 `dynamic_parts_list` 中的敏感字串替換成 `var_<hash>` 形式的安全變數名，**之後才**寫入 `generated_code.txt`（第447–448行）並送進 `aggregate_functions()` 做函式整併、最終輸出 `generated_code.py`。
- **能否保證cookie明文值一定會被列入 `dynamic_parts_list` 而被混淆，取決於上游LLM是否正確把該值標記為`dynamic_parts`**——這是機率性的LLM判斷結果，不是程式碼保證的邏輯。若LLM漏判（或人類直接手動組資料），該cookie明文值就會原樣留在 `generated_code.py` 這個**會被使用者長期保存、甚至可能被分享/commit的成品檔案**裡。
- 而且即使混淆邏輯正確執行，`generate_code()` 呼叫LLM生成一般（非cookie）節點程式碼時的prompt本身（第225–245行）仍要求LLM「Return a dictionary with the keys as the original parsed values content (needs to be hardcoded)」——即明確要求LLM把解析出來的值**硬編碼**進生成的程式碼裡，這對一般業務參數合理，但若解析出的值恰好是token/session相關值，就是把敏感值寫死進最終腳本。
- **結論：沒有觀察到蓄意把cookie/token硬編碼留在最終產物的設計意圖（有混淆機制），但混淆完全依賴LLM分類正確與否，屬於「盡力而為」而非「架構保證」，不能視為可靠的資安控制。**

### 低：可能透過LangSmith把整個prompt歷史外洩給第三個廠商（未能驗證是否實際觸發）

- `pyproject.toml` 依賴中含 `langsmith`（LangChain的官方追蹤/可觀測性SaaS），且整個agent走 `langgraph`/`langchain-openai`。原始碼中**沒有**看到任何主動停用LangSmith追蹤的設定（例如未見 `LANGCHAIN_TRACING_V2=false` 或程式內覆寫）。
- LangChain生態預設情況下若使用者環境變數中設有 `LANGCHAIN_TRACING_V2=true` 與 `LANGCHAIN_API_KEY`（常見於開發者機器上為了偵錯其他LangChain專案而全域設定），本專案在不知情下會把所有prompt（含上述含敏感值的curl/回應內文）也送一份到LangSmith雲端。
- 這屬於**條件式風險**，觸發與否完全取決於使用者自己機器的環境變數，無法從repo本身斷定是否會發生，誠實標註「未能驗證是否實際觸發」，但值得使用前主動確認 `LANGCHAIN_TRACING_V2` 未開啟。

### 低：法遵／服務條款風險（非本次技術重點，但一併記錄）

- 本工具的設計目的就是「逆向工程目標網站未公開的內部API」並繞過官方SDK/API的使用條款與流量控管，這已在來源新聞（20260813.md）中提及。技術面補充：`excluded_keywords`/`excluded_header_keywords`會刻意排除Sentry、Datadog、Amplitude等監控與追蹤服務的請求（`har_processing.py`第7–39行），這只是為了減少LLM分析噪音，並非規避偵測的設計，但客觀上也降低了被目標網站異常流量監控系統標記的機率——使用者需自行評估此舉是否構成規避服務條款中「禁止自動化存取」條款的行為，以及目標平台bot-detection/ToS執法風險。

### 未能驗證的項目

- OpenAI API是否確實遵守「API資料不用於訓練」政策（依賴OpenAI官方承諾，非本repo可控）。
- 使用者本機`.env`中`OPENAI_API_KEY`的保護（依賴使用者作業系統/檔案權限設定，repo本身無額外加密）。
- www.integuru.com目前正式版本（非本v0 repo）是否已改善上述問題——README明確說目前產品已搬到該站，原始碼未公開，本評估範圍僅限本v0 repo。
- SECURITY.md：repo中**不存在**此檔案，無官方安全通報管道、無漏洞回報政策。

## 三、建議的安裝與使用方式

1. **只用假帳號/測試帳號跑，絕不用在含真實金融、醫療、個資的正式帳號上**——因為Cookie/HAR中的敏感值有機會原樣送進OpenAI。
2. **執行環境務必隔離**：使用一次性容器或VM，跑完立即銷毀，`network_requests.har`與`cookies.json`用完後手動刪除，不要留在長期使用的工作機上。
3. **執行前檢查機器環境變數**：確認未設定 `LANGCHAIN_TRACING_V2=true`，避免prompt被同時送去LangSmith。
4. **執行前先手動檢視 `network_requests.har`／`cookies.json`**，人工遮蔽任何非目標動作所需的敏感回應內容（例如把不相關回應內文清空），再交給Integuru分析，降低盲目全量上傳的暴露面。
5. **產出的 `generated_code.py` 使用前務必人工審查**，搜尋是否殘留任何看起來像token/session值的硬編碼字串（例如長度異常的hex/base64字串），而不要預設混淆機制一定生效。
6. **不要把 `generated_code.py`、`network_requests.har`、`cookies.json` commit進任何版本控制或分享給他人**，即便`.gitignore`已預設排除，仍建議額外人工確認 `git status`。
7. 使用前確認目標網站服務條款是否允許此類自動化／逆向工程行為，避免法遵風險。

## 四、PoC 的環境要求

- Python 3.12（`pyproject.toml` 限定 `>=3.12,<3.13`）、Poetry套件管理。
- Playwright（需另外 `playwright install` 瀏覽器執行檔）以執行 `create_har.py` 開啟瀏覽器供使用者手動登入。
- 有效的 `OPENAI_API_KEY`（存於`.env`），且帳號建議可存取o1-preview或同等級模型（README第45行建議）。
- 需要人工介入：使用者必須親自完成登入與2FA後按Enter，工具才會擷取cookies——這代表**攻擊者若要濫用此工具，仍需先拿到受害者本人的登入能力**，此工具本身不是憑空竊取憑證的攻擊工具，而是「使用者自願把自己的合法session交給AI分析」的風險模式，威脅模型偏向資料外洩/供應鏈信任問題，而非帳號盜用工具。
- 無Docker化或沙箱設定，需自行搭建隔離環境（見上方建議）。

## 五、給決策者的一句話

Integuru v0 讓你把自己完整的登入session（HAR+Cookie）交給OpenAI分析換取自動生成的爬蟲/整合程式碼，Cookie標頭本身有被過濾，但URL、request body、HTTP回應內文中的token與敏感資料完全沒有遮罩機制地送進雲端LLM，且生成程式碼是否會殘留明文憑證完全取決於LLM判斷是否正確——除非只拿測試帳號在隔離環境跑且用後即刪，否則不建議在任何正式或含真實個資的帳號上使用。
