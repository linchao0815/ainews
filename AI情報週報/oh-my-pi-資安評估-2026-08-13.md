# oh-my-pi 資安評估

> 對象：[can1357/oh-my-pi](https://github.com/can1357/oh-my-pi)（MIT License）
> 起因：[20260813.md](20260813.md)「GitHub趨勢｜終端AI coding agent oh-my-pi」該則新聞建議評估其hash-anchored編輯法，導入前先做資安查核
> 評估日期：2026-08-13　評估版本：commit `dee2196` (2026-08-13)，package version `17.2.15`
> 方法：shallow clone 原始碼實際檢視工具執行權限模型、桌面控制/debugger功能範圍、遙測路徑，非僅閱讀README

## 結論

oh-my-pi 的工程品質與文件透明度在同類專案中偏高（approval 模型有完整規格文件且與程式碼一致、secret 遮罩機制設計嚴謹、auto-QA 遙測有明確 consent gate），但**預設執行模式（`tools.approvalMode` 預設值 `yolo`）對 shell 執行/檔案寫入/瀏覽器與桌面控制一律自動放行、不詢問使用者**，且啟用後的 `computer`（桌面控制）與 `debug`（真實 debugger 掛載）工具都明確聲明「非沙箱、可觸及完整 host 權限」。安裝腳本無雜湊/簽章驗證下載的執行檔。建議結論：**可在隔離帳號/VM 且手動改為非 yolo 模式（`write` 或 `always-ask`）下試用，不建議以預設設定在正式工作環境（尤其含敏感資料或生產憑證的主機）直接安裝執行**。

## 二、風險項目

### 高：預設「yolo」放行模式 —— shell/檔案寫入/瀏覽器/桌面控制皆無需使用者確認

`packages/coding-agent/src/config/settings-schema.ts` 第3677-3680行：
```ts
"tools.approvalMode": {
  type: "enum",
  values: ["always-ask", "write", "yolo"] as const,
  default: "yolo",
```
`docs/approval-mode.md` 明確定義 `yolo` 模式「auto-approves read, write, exec — none 需要 prompt」。這代表一個全新安裝、未手動改設定的 oh-my-pi，agent 執行任意 shell 指令（`bash` 工具，tier=`exec`）、寫入/刪除檔案、啟動瀏覽器/桌面自動化,全部預設自動放行，不會跳出任何確認視窗。文件本身也承認這只是「安全網」而非沙箱：`bash.patterns` 對 `rm -rf /`、fork bomb、遠端抓取後執行等**極端**模式仍會強制 prompt，但除此之外的一般破壞性操作（例如刪除專案外的檔案、寫入 `~/.ssh/authorized_keys`、對外傳送資料的 curl POST）在 yolo 模式下完全不受阻。

對照之下，Claude Code / Codex CLI 等主流同類工具的預設行為都是逐步詢問或至少要求使用者顯式開啟 auto-approve/yolo，oh-my-pi 反其道而行，把最寬鬆模式設為出廠預設值，這是本評估中風險最高的單一項。

### 高：`computer`（桌面控制持久化 JS 執行）功能範圍等同完整 host 存取，非沙箱

`docs/computer-use.md` 第46-55行為關鍵原文：
> `code` runs with top-level `await` in a persistent, full-host-access Bun session. [...] This is **not a sandbox**. The evaluated code still has the worker's full Bun/Node host access, including `process`, `require`, and `fs`, so `read_only` does not prevent mutation through arbitrary host APIs.

即使呼叫端聲明 `read_only: true`（只為了approval分級與擋住 `desktop` facade 本身的輸入/剪貼簿寫入方法），送進去的 JS 仍可透過 `require('fs')`、`process` 等原生 API 任意讀寫整台主機檔案系統、執行子行程，`read_only` 只是「信任聲明」不是靜態分析或沙箱隔離。此工具預設關閉（`computer.enabled: false`），一旦專案或使用者主動開啟，在預設 `yolo` approval 模式下等於讓 LLM 對整台桌面（螢幕截圖、原生輸入、剪貼簿、任意應用程式視窗操作）獲得無條件執行權。文件本身也建議「Use a dedicated account or VM for risky work」，等於官方承認這需要額外隔離才安全。

### 中：`debug` 工具（lldb/dlv/debugpy 等）掛載範圍不限於目前專案，可 attach 任意本機 PID 或遠端 port，並支援任意記憶體讀寫

`docs/tools/debug.md` 顯示 `attach` action 只需要 `pid` 或 `port`（第46-47、69行），沒有任何限制「只能 attach 屬於目前 cwd/專案的行程」。內建 adapter 清單含 `gdb`、`lldb-dap`、`codelldb`、`debugpy`、`dlv`、`js-debug-adapter`、`netcoredbg` 等（第159行）。`write_memory`、`custom_request`（任意 DAP 指令）、`evaluate`（預設 `repl` context，可轉發原始 debugger 指令）等 action 理論上可以：
- attach 到系統上任何以相同使用者權限執行的行程（含使用者本機上其他無關程式，只要能取得其 PID）
- 對目標行程做任意記憶體寫入（`write_memory`）
- 透過 `runInTerminal` 反向請求，用 `ptree.spawn()` 產生子行程

Approval 上這些屬於 `exec` tier（唯讀動作如 `stack_trace`/`variables` 才是 `read`），但同樣受 yolo 預設模式影響——若使用者未調整 approval 模式，debugger 掛載到任意 PID 並執行記憶體寫入不會有任何確認提示。此工具**預設啟用**（`debug.enabled` 預設 `true`，見 `docs/tools/debug.md` 第124行），比 `computer` 的「預設關閉」風險更高一階——只是預設沒有可攻擊目標（沒有現成 PID/port 可用時工具無害）。

### 中：安裝腳本（`curl | sh`）下載預編譯二進位無雜湊/簽章驗證

`scripts/install.sh` 第226-233行下載流程：
```sh
BINARY_URL="https://github.com/${REPO}/releases/download/${LATEST}/${BINARY}"
curl -fsSL ... "$BINARY_URL" -o "${INSTALL_DIR}/omp"
chmod +x "${INSTALL_DIR}/omp"
```
全程沒有比對 `scripts/ci-release-checksums.ts` 產生、隨 release 一併發布的 `SHA256SUMS.txt`。也就是說 checksum 有做（供使用者手動驗證），但官方安裝腳本本身不驗證，若 GitHub Release 資產遭竄改或 CDN/DNS 被劫持，使用者會無警覺地執行未經驗證的二進位。`scripts/install.ps1`（Windows 版）未逐行核對，但同樣走 GitHub Releases 直接下載模式，推測有相同缺口（因時間限制未逐行讀完，此點為推測而非逐行查證結論）。

### 低：Auto-QA 遙測預設「啟用但需 consent」，屬於灰色地帶

`dev.autoqa` 預設 `true`，代表系統會嘗試在每次工具異常行為時準備一筆「grievance」記錄並詢問使用者是否同意上傳到 `qa.omp.sh`（`packages/coding-agent/src/tools/report-tool-issue.ts` 開頭註解與 `isAutoQaEnabled()` 邏輯）。實際上傳需要明確同意，且無 UI 環境時預設不收集，設計上算負責任。列為低風險僅因「預設開啟自動化資料蒐集提示」在部分企業合規情境下仍可能需要額外說明（例如在非互動 CI 中設 `PI_AUTO_QA_PUSH=1` 會繞過對話框直接上傳）。

### 未能驗證的項目
- Windows 版安裝腳本 `scripts/install.ps1` 未逐行核對是否有等效的雜湊驗證缺口。
- Rust crates（`crates/pi-*`, `crates/vendor/*`）與 npm 依賴樹未逐一跑 `cargo audit` / `npm audit`，僅抽查根 `Cargo.toml`（workspace 版本 17.2.15，未見異常 patch 來源，`[patch.crates-io]` 僅替換 `brush-core` 為本地 vendor 版本，屬正常做法）；未發現明顯過時或高風險相依套件，但未做完整供應鏈掃描。
- 瀏覽器自動化工具（`browser`，CDP/DOM 控制）文件與 `computer` 工具分開存在（`docs/tools/browser.md` 提及但未深入讀取其原始碼），其「持久化 JavaScript 執行」是否比 `computer` 工具的 host-JS 執行範圍更受限（例如限制在瀏覽器 renderer sandbox 內）未逐行查證。

## 三、建議的安裝與使用方式

1. 在隔離的測試帳號或一次性 VM/容器內安裝，不要用日常工作帳號或含生產憑證的主機。
2. 安裝前手動下載 release 資產與對應的 `SHA256SUMS.txt`，自行執行 `sha256sum -c` 驗證後再執行，不要直接 `curl | sh`。
3. 安裝後、第一次執行前，先在 `~/.omp/agent/config.yml` 明確設定：
   ```yaml
   tools:
     approvalMode: always-ask   # 或至少 write
   computer:
     enabled: false             # 除非確定需要桌面控制且已隔離環境
   debug:
     enabled: false             # 除非確定需要且已限制可觸及的行程/port
   ```
   不要沿用預設的 `yolo`。
4. 若需要使用 `computer`（桌面控制）功能，僅在專用測試機/VM 內開啟，且維持 `approvalMode: write` 以上（讓 mutation 類呼叫仍需確認）。
5. 若組織有合規要求，明確評估是否接受 `dev.autoqa` 預設開啟的行為，必要時在 config 顯式設 `dev.autoqa: false`。

## 四、PoC 的環境要求

- 一次性 VM 或容器（無 SSH 金鑰、無雲端憑證、無生產資料庫連線資訊掛載進環境）。
- 網路層面建議先以 egress 白名單/監控觀察 agent 實際對外連線目標（尤其在測試 `computer`/`debug` 工具時）。
- 測試 `computer` 工具需要另外授予 OS 層級權限（macOS Screen Recording + Accessibility；Linux 需 X11/AT-SPI 或 Wayland portal），應在快照/可還原的 VM 上進行，測試後整台回滾。
- 測試 `debug` 工具 attach 功能時，PoC 環境內不應存在任何有價值的其他行程（因為 attach 只需 PID，範圍可能超出預期目標）。

## 五、給決策者的一句話

oh-my-pi 文件與 approval 框架設計嚴謹，但出廠預設是「全自動放行 + 一啟用桌面控制就等於給 LLM 完整 host 執行權」，導入前必須先手動切換成非 yolo 模式並在隔離環境試跑，不要直接在正式機器上用預設值安裝。
