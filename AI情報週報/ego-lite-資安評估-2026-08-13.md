# ego-lite 資安評估

> 對象：[citrolabs/ego-lite](https://github.com/citrolabs/ego-lite)（MIT License）
> 起因：[20260813.md](20260813.md)「GitHub趨勢｜瀏覽器自動化工具 ego-lite」該則新聞建議試用評估，導入前先做資安查核
> 評估日期：2026-08-13　評估版本：commit `c46a439e7fbad90ad33dbea6c6af329b6009809f`（2026-08-10，shallow clone 當下 HEAD）
> 方法：shallow clone 原始碼實際檢視安裝腳本、通訊機制、遙測相關程式碼，非僅閱讀README

## 結論

ego-lite 這個 GitHub repo **只是「連接層」的開源部分**（`ego-browser` CLI/skill，供 Claude Code、Codex 等 agent 呼叫），實際的瀏覽器本體（Chromium/Electron 應用程式、自動更新機制、與 agent 溝通的底層通道）是**閉源的 macOS App**，以 .dmg 下載安裝，本次查證完全無法觸及其原始碼；同時安裝腳本本身**沒有做任何雜湊/簽章驗證，且刻意剝除 macOS Gatekeeper 的 quarantine 屬性**，一旦下載來源被竄改或 CDN 遭劫持，等同繞過作業系統的第一道防線直接安裝執行檔。開源部分（ego-browser CLI）程式碼品質不錯、沒有找到遙測/資料外傳程式碼，但「task space」的隔離只是分頁層級，底層登入態（cookie/session）是與使用者主瀏覽器**共用不隔離**的，文件也明白寫著這是設計如此。**建議結論：不建議現階段直接開放給同仁在有正式帳密登入狀態的機器上試裝；如要試用，僅限在乾淨的獨立測試帳號/測試機、且暫不匯入公司系統登入態的前提下小範圍評估。**

## 二、風險項目

### 高：實際瀏覽器本體是閉源軟體，多項核心資安宣稱無法查證
`README.md`（第20-75行）宣稱「your browsing data stays on your device」「ego lite only records whether you opted into Chrome migration」，但這個 GitHub repo **完全不包含瀏覽器本體**。`CONTRIBUTING.md` 第28-30行明講：「This repo does not ship the browser binary; the browser must be installed separately.」瀏覽器是從 `cdn.ego.app` 下載的 macOS .dmg（見 README 第10-11行、`skills/ego-browser/scripts/install.sh` 第7-8行）。也就是說：
- Chromium/Electron 本體的沙盒設計、是否真的有遙測回傳、自動更新的驗簽機制，全部藏在閉源二進位檔內，本次查證**完全無法驗證**，只能信任廠商片面聲明。
- 對公司情境而言：一旦同仁在此瀏覽器登入公司信箱、內部系統、VPN 入口等敏感帳號，資料實際去向完全不透明，無從稽核。

### 高：安裝腳本沒有雜湊/簽章驗證，且主動剝除 Gatekeeper quarantine 屬性
`skills/ego-browser/scripts/install.sh`：
- 第161-162行：`curl -fL --retry 3 --output "$dmg_path" "$dmg_url"` 下載 DMG，**全程沒有任何 checksum、GPG 簽章、或 codesign 驗證**步驟。
- 第186-188行、第70-74行 `strip_quarantine_attributes()`：對下載回來、尚未經過使用者手動確認的 App 執行 `xattr -dr com.apple.quarantine`，**主動關閉 macOS Gatekeeper 對「網路下載檔案」的檢查**，讓使用者第一次啟動時不會看到「無法驗證開發者」的警告。
- 第190-196行：若 `/Applications` 下已有同名 App，會用 `run_with_sudo_if_needed rm -rf "$APP_PATH"` 直接砍掉重裝，且第41-53行的 `run_with_sudo_if_needed` 在權限不足時會自動 fallback 呼叫 `sudo`。

三者疊加的攻擊面：若 `cdn.ego.app` 遭入侵、DNS/CDN 被劫持，或使用者在不安全網路下載，這支腳本會**在沒有任何完整性檢查的情況下，剝除系統防護並以 sudo 權限安裝執行**。這是本次查證中最嚴重的單一風險點。

### 高：Agent 的瀏覽任務與使用者主要瀏覽 session「不隔離」，只是分頁隔離
`skills/ego-browser/SKILL.md` 第61行明文：「Each task space has its own set of tabs but **inherits the current user's login state by default**」；`CONTRIBUTING.md` 第183行再次確認：「A `Task Space` is an isolated browsing context provided by ego-browser: it owns its own tab set **but inherits the user's login state**.」
這代表使用者擔心的「AI agent 能不能被誘導做出超出授權的操作」風險是真實存在的：task space 不是資安邊界，只是 UI/分頁層級的區隔，agent 與使用者共用同一份 cookie/session/已登入狀態。若 agent 被 prompt injection（例如瀏覽到惡意頁面而被誘導執行非預期操作）騎劫，它能觸及的帳號權限與使用者本人完全相同,包含銀行、公司系統等敏感登入態。

### 中：自動更新機制的驗證方式不可考
`package/ego-browser/src/update-notice.ts` 只是把「App 端」透過 `ego.getBrowserVersion()` 回傳的 `updateAvailable`/`mandatory` 資訊組成一行提示文字給 agent 看（第70-85行），實際更新的下載/安裝/簽章驗證邏輯完全在閉源 App 內執行，**開源部分看不到、也無法驗證更新包是否有做雜湊或程式碼簽章檢查**。且程式碼支援 `mandatory: true` 的強制更新語意（第32行、第83行），意味 App 端可以強制推送更新，但驗證機制同樣不可考。

### 中：Agent 與瀏覽器間的通訊機制細節不可考
`package/ego-browser/src/browser-runtime.ts` 顯示 CDP 是透過 `globalThis.ego.sendCDPMessage()` 這個由 App 注入的原生橋接物件送出（第25-36行、第44-70行），**不是走一般認知中「本機開一個 TCP/WebSocket port（如 9222）」的模式**——全庫搜尋 `127.0.0.1`/`localhost`/`ws://`/`9222`/`remote-debugging` 等關鍵字均無結果。`ego-browser` 執行檔實際上是被安裝在 App bundle 內部（`install.sh` 第84行：`$app_path/Contents/Frameworks/*.framework/Versions/Current/Helpers/ego-browser`），推測是以行程內橋接（native binding）方式與主程式溝通，而非對外監聽的網路埠。這點對「會不會被區網其他機器連線」這個疑慮是相對正面的訊號，但**橋接通道本身的實作、是否有任何行程間的存取控制，都在閉源 App 內，無法從本 repo 查證**。

### 低：npx 安裝路徑與 GUI App 寫入 agent skills 目錄的行為無法從本 repo 查證
README 第41行「ego lite adds the `ego-browser` skill to every agent's skills directory on your machine」、第43-49行 `npx skills add citrolabs/ego-lite`。這兩種安裝路徑實際寫入 `~/.claude`、`~/.codex`、`~/.cursor` 等目錄的邏輯，分別在閉源 App 內、或依賴第三方 `skills`（npx）套件的實作，**本次查證範圍內（本 repo 原始碼）找不到對應程式碼可供核實**，需視為未能驗證，而非「已排除風險」。

### 低：依賴套件抽查未見明顯過時或高風險項目
`package/ego-browser/package.json` 運行期依賴僅 `acorn@^8.16.0`（輕量 JS parser），開發期依賴 `esbuild@^0.28.1`、`rollup@^4.60.4`、`typescript@^5.8.3` 版本均屬近期版本，未見已知嚴重 CVE 的明顯訊號；但本次僅抽查未逐一比對 CVE 資料庫。

### 資訊：無 SECURITY.md
Repo 根目錄與各子目錄下皆未找到 `SECURITY.md`，沒有正式的漏洞通報管道與 disclosure policy，僅有一般的 GitHub Issues。開發團隊自稱 CitroLabs（`contact@citrolabs.ai`，`LICENSE` 第3行 Copyright (c) 2026 CitroLabs），組織身分可查但無進一步實體資訊佐證。

## 三、建議的安裝方式

若決定進行 PoC，建議比照以下方式降低風險：

1. **不要在有公司系統/VPN/信箱登入態的主力工作機上安裝**——選一台可重灌、無正式帳密的獨立測試機或乾淨的虛擬機（注意官方僅支援 macOS，需實體或授權虛擬環境）。
2. 安裝前**手動**下載 README 中列出的 `.dmg` 連結，用 `codesign -dv --verbose=4 <path>` 與 `spctl -a -vv <path>` 自行核對簽章與開發者身分，不要直接執行 `install.sh` 讓它自動剝除 quarantine——寧可手動確認一次 Gatekeeper 警告內容再決定是否放行。
3. 全程使用測試帳號（測試信箱、測試網銀 sandbox 若有、測試版公司系統帳號），不要匯入 Chrome 真實登入態（安裝時的 Chrome migration 詢問選「否」）。
4. 觀察期間用 Little Snitch / Lulu 等出站流量監控工具，記錄 App 實際對外連線的網域，交叉比對官方聲明。
5. 限制在單機小範圍（1-2 位同仁）試用 1-2 週，蒐集實際對外連線紀錄與行為觀察後再決定是否擴大。

## 四、PoC 的環境要求

- 僅支援 macOS（Apple Silicon 或 Intel），Windows/Linux 尚在 roadmap，公司若主力為 Windows，此工具目前不適用。
- 需要一台可重灌或用完即丟的測試機/VM，不可用生產或個人工作機。
- 需準備測試用帳號體系（不使用真實公司系統/銀行/信箱登入態）。
- 需要出站流量監控能力（Little Snitch/Lulu 或公司網路層 DLP）以彌補閉源部分無法查證的落差。
- 需要一位對 macOS Gatekeeper / codesign 有經驗的同仁協助手動驗證安裝包簽章，因為腳本本身不做這件事。

## 五、給決策者的一句話

ego-lite 開源的「連接層」程式碼乾淨、沒查到遙測外傳，但核心瀏覽器是閉源軟體、安裝腳本會主動關閉系統防護且不做任何完整性驗證、agent 與使用者共用同一份登入態——現階段只適合在乾淨測試環境小範圍 PoC，不適合直接推廣到會接觸公司真實帳密的日常工作機。
