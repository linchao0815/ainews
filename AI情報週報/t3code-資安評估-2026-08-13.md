# T3 Code 資安評估

> 對象：[pingdotgg/t3code](https://github.com/pingdotgg/t3code)（MIT License）
> 起因：[20260813.md](20260813.md)「GitHub趨勢｜T3 Code遠端操控coding agent」該則新聞建議資安與工程主管評估其遠端連線機制，導入前先做資安查核
> 評估日期：2026-08-13　評估版本：commit `6bc6cb6b`（2026-08-12）
> 方法：shallow clone 原始碼實際檢視遠端連線架構、身份驗證機制、傳輸加密、中繼伺服器信任模型，非僅閱讀README

## 結論

T3 Code 的核心遠端連線架構設計得比一般個人專案成熟：採 bootstrap／session 兩段式權杖、一次性配對碼、DPoP proof-of-possession、可撤銷 session，且官方明確建議走 Tailscale/SSH 而非公開暴露；但預設「Full access」執行模式代表 agent 收到指令後預設無人工確認即可執行任意 shell 指令與檔案修改，這才是真正的風險核心——手機被盜或配對連結外流，攻擊者即可在配對有效期內於公司機器上以「Full access」模式下達指令，等同遠端任意執行。建議結論：**可在嚴格控管的沙箱環境（獨立測試機／一次性 VM、僅限 Tailscale 私網、強制 Supervised 模式）由少數同仁試裝評估，暫不建議接上任何生產或含機敏資料的工作機**，因為這是「手機/網頁觸發內部機器執行指令」的架構，風險評估重點在遠端連線安全與預設執行模式，而非工具本身的 agent 操控功能。

## 一、查證通過的項目

| 項目 | 查證結果 |
|---|---|
| 傳輸加密 | 官方建議走 Tailscale（TLS/WireGuard）或使用者自備 HTTPS/WSS；程式碼明確拒絕從 `https://app.t3.codes` 連到 `http://`/`ws://` 明文端點（mixed-content 阻擋），見 `.plans/19-remote-endpoints-hosted-static.md` 與 `docs/user/remote-access.md` |
| 身份驗證機制 | 非單純固定密碼/token。`apps/server/src/auth/EnvironmentAuth.ts` 實作 bootstrap credential（一次性配對碼，`desktop-bootstrap`/`one-time-token`）與 session credential（`browser-session-cookie`/`bearer-access-token`）分離，session 可有 TTL、可撤銷；WebSocket 升級走獨立 `wsTicket` 短效票證（`WEBSOCKET_TICKET_QUERY_PARAM`），而非長期 token 直接掛在 URL 上 |
| DPoP 防重放/防竊用綁定 | `apps/server/src/auth/dpop.ts`、`infra/relay/src/auth/DpopProofs.ts` 實作 RFC 9449 風格 DPoP proof-of-possession，將 access token 綁定用戶端金鑰指紋（`proofKeyThumbprint`），token 被截獲也無法在別的裝置重放；`DpopProofs.verifyAndConsume.test.ts` 顯示有針對重放攻擊的測試 |
| Session 可視化與撤銷 | `EnvironmentAuth.ts` 提供 `listSessions`/`revokeSession`/`revokeOtherSessionsExcept`，CLI `t3 auth` 可列出並撤銷已配對裝置與 pairing link（`docs/user/remote-access.md` 「Managing Access Later」） |
| Hosted 網頁版不留存 token | `docs/user/remote-access.md`：配對連結把 token 放在 URL fragment（`#token=`），不會送到 `app.t3.codes` 的伺服器端，且 hosted app 不代理流量，瀏覽器直連使用者自己的 backend |
| 官方安全政策與弱點回報管道 | `apps/marketing/src/pages/security-policy.astro` 有正式 Security Policy，含 safe-harbor、`security@ping.gg` 回報信箱、一個工作天內回覆承諾 |
| License 寬鬆、原始碼公開可稽核 | MIT License（`LICENSE`），monorepo 完整原始碼可讀，不是黑箱二進位 |
| 遙測預設匿名且可關閉 | `apps/server/src/telemetry/AnalyticsService.ts` 使用 PostHog，`T3CODE_TELEMETRY_ENABLED` 環境變數可關閉，員工試裝前可先停用 |
| CI 存在 | `.github/workflows/ci.yml`、`release.yml`、`pr-vouch.yml`、`pr-size.yml` 等流程齊備，PR 有自動信任分級（vouch）與尺寸標記 |

## 二、風險項目

### 高：預設「Full access」執行模式＝遠端指令可無人值守自動執行（含背景常駐服務）

`docs/user/permission-modes.md` 明載：新建 thread 若未特別選擇，**預設就是「Full access」**——「allow commands and edits without prompts... The agent runs unattended until it finishes or asks a question of its own.」也就是說，只要攻擊者（或被盜用帳號）能建立一個新 session/thread 並下達指令，agent 會直接執行 shell 指令與檔案修改，不需要人工按確認。

同時 `docs/user/background-service.md` 顯示 T3 Code 在 Linux 上可安裝為 systemd 常駐服務（`npx t3 service install`），開機自動啟動、登出後持續運行——這代表公司工作機一旦裝了背景服務並開啟遠端配對，即便沒人在電腦前，遠端連線建立後 agent 仍可依 Full access 模式執行指令。

「Supervised」模式雖存在（逐一詢問核准），但不是預設，仰賴使用者手動每次切換；若同仁沿用預設值試裝，等於把「手機能不能觸發工作機任意執行」的問題，退化成單純「配對憑證有沒有外流」的問題。

### 高：遠端身份驗證與中繼伺服器信任模型——配對憑證＝短期萬能密碼

`docs/user/remote-access.md`「Security Notes」原文明講：「Treat pairing URLs and pairing tokens like passwords」「Anyone with a valid pairing credential can create a session until that credential expires or is revoked」。配對碼本質上是一次性但效期內完整等同帳密（`PairingGrantStore.ts` 的 `issueOneTimeToken`，`ttl` 可設定，預設走 5 分鐘等短效但可由呼叫端調整）。若配對連結透過截圖、剪貼簿、瀏覽器歷史、Slack/Email 轉傳外流（文件自己也承認這個風險：「it can still be exposed through browser history, screenshots, logs, or copy/paste」），在其有效期內任何人皆可完成配對並取得 session，之後即可持續下指令直到被撤銷。

中繼信任模型部分：核心 LAN/Tailscale/SSH 配對流程**不經過** pingdotgg 的伺服器（`docs/user/remote-access.md`：「Hosted pairing does not proxy traffic through T3 Code. The browser still connects directly to the backend URL」）——這點對供應鏈風險是利多，代表 pingdotgg 平時看不到、也轉發不了使用者的 agent 對話內容。但選配的付費「T3 Connect」代管通道（`infra/relay/`）走 pingdotgg 營運的 Cloudflare 式中繼基礎設施（`infra/relay/src/environments/EnvironmentConnector.ts` 以簽章 JWT 做 mint/connect 授權，`infra/relay/src/zone.ts`、`ManagedEndpointAllocations.ts` 管理代管網域）；若啟用 T3 Connect，其 DNS 配置與連線授權即交由 pingdotgg 的中繼服務仲介，一旦該服務被入侵，理論上可影響經其代管網域轉發的連線授權（雖然仍需搭配裝置端 session/DPoP 憑證才能真正冒充使用者——單純中繼被入侵**不足以**直接偽造完整 session，但會擴大攻擊面）。**未能驗證**代管通道的資料面是否對 pingdotgg 端不透明（是否為單純 DNS/TLS-passthrough 或有終止 TLS 之處），需要更深入追蹤 Cloudflare Worker 層程式碼才能下定論。

### 中：配對／驗證流程未見速率限制（brute-force 防護）

在 `apps/server/src/auth/`、`infra/relay/src/auth/` 全目錄搜尋 `rateLimit`/`throttle`/`maxAttempts`/`429` 等關鍵字均**查無結果**。也就是說目前程式碼層面看不到針對配對 token 猜測或重複驗證失敗的速率限制/鎖定機制。配對 token 本身雖然理論上高熵（`Crypto.Crypto` 產生），但沒有主動的暴力破解防護是設計上的缺口，尤其若日後開放非 loopback 綁定的公開暴露場景。

### 中：安裝與更新鏈缺乏雜湊/簽章驗證的公開紀錄

`README.md` 主要安裝方式為 `npx t3@latest`（走 npm registry 標準機制，沒有另外的一鍵 curl|bash）——這點比許多同類專案安全。但桌面版透過 GitHub Releases /winget/Homebrew/AUR 分發，在 `.github/workflows/release.yml` 及全庫搜尋中**未查到** `sha256`/`checksum`/`cosign`/`sigstore`/SLSA provenance 等字樣，代表官方公開的原始碼中沒有明顯的產物簽章/校驗和驗證流程紀錄（可能實際簽章在 electron-builder/winget/homebrew 各自流程中處理，但未能在原始碼中直接驗證）。另外 `README.md` 中「如果你真的想貢獻」段落要求安裝第三方工具鏈 `vite.plus`（`curl -fsSL https://vite.plus | bash`），這是給貢獻者用的建置工具鏈依賴，非終端使用者安裝流程，但同樣缺乏雜湊驗證，屬於供應鏈上的次要風險點。

### 低：治理與貢獻政策對供應鏈信任的意涵

`CONTRIBUTING.md` 明白寫「We are not actively accepting contributions right now」，外部 PR 預設 `vouch:unvouched` 標籤，只有 `.github/VOUCHED.td` 白名單內約 30 位帳號被信任。這代表目前程式碼實質上仍由核心團隊把關（單一維運方風險 vs. 外部投毒風險的取捨）：優點是外部惡意 PR 很難悄悄混入；缺點是專案高度集中於單一團隊（pingdotgg / T3 Tools Inc.），一旦該團隊帳號或建置管線被入侵，缺乏廣泛社群審查作為第二道防線，且長期維護的存續高度依賴單一小型團隊（項目自陳「we are very very early」「expect bugs」）。

### 低：依賴套件抽查

`package.json` 使用 pnpm workspace + catalog 版本管理，核心執行環境要求 Node `^24.13.1`（相對新，非陳舊過時的執行環境）。`patches/` 目錄下對多個第三方套件（`@clerk/expo`、`react-native-*`、`effect` 等）有自訂 patch，數量偏多，代表專案大量依賴仍在快速變動的新興函式庫（如 `effect` 4.0.0-beta 版），穩定性與長期維護風險需留意，但未發現已知高風險 CVE 套件版本（僅抽查，非完整 SCA 掃描，**未能驗證**全量相依樹）。

## 三、建議的安裝與使用方式

1. 僅在一台**與公司網域、VPN、共用帳密體系隔離**的獨立測試機或一次性 VM 上安裝，不使用任何接觸生產資料/客戶資料的工作機。
2. 安裝時透過官方 `npx t3@latest`（npm registry 標準分發），避免 GitHub Releases 二進位（缺乏可驗證的雜湊/簽章公開紀錄）；如需桌面版，優先用 winget/Homebrew 這類有平台層驗證的通路而非直接下載安裝檔。
3. **連線僅限 Tailscale 私網或 SSH tunnel**，不對公網或公司內部 LAN 廣播開放（`t3 serve --host 0.0.0.0` 類設定禁止）；不啟用付費 T3 Connect 代管通道，直到中繼信任模型被進一步查證。
4. 每個 thread **手動切換為「Supervised」模式**，不要使用預設的「Full access」；試裝期間定期以 `t3 auth` 檢視並清除不再需要的 session/pairing link。
5. 關閉遙測：設定環境變數 `T3CODE_TELEMETRY_ENABLED=false`。
6. 不安裝 Linux systemd 背景常駐服務（`t3 service install`），僅在需要時手動啟動、用畢即關閉，避免無人在場時仍可被遠端配對觸發指令。
7. 試裝範圍限定 1-2 位工程主管／資安人員在可拋棄的 repo/worktree 中操作，觀察配對流程、session 撤銷、Supervised 模式下的實際核准體驗，再決定是否擴大。

## 四、PoC 的環境要求

- 獨立測試機或 VM（非公司網域加入、非生產環境），作業系統建議 macOS/Windows 桌面版或 Linux + `npx t3@latest`（勿裝 systemd 背景服務）。
- Node.js `^22.16 || ^23.11 || >=24.10`（依 README 要求）。
- 至少一組已安裝並登入的 coding agent（Claude Code / Codex / Cursor CLI 等）之測試帳號，避免使用正式生產金鑰。
- Tailscale 帳號（建議用個人/測試 tailnet，不接公司既有 tailnet）作為驗證私網配對的傳輸層。
- 一支測試用手機（安裝 T3 Code App）用於驗證掃碼配對、session 撤銷、Supervised 模式核准流程。
- 全程錄影/截圖配對連結產生與使用過程，驗證「配對連結是否經由 URL fragment、是否出現在瀏覽器歷史/剪貼簿」等文件中自述的風險點。

## 五、給決策者的一句話

T3 Code 的配對與 session 機制設計不差，但預設「Full access」等於遠端配對成功後即可無人工確認地在目標機器上執行任意指令，這才是核准前必須先鎖死的關卡，不是工具好不好用的問題。
