# Strix 資安評估

> 對象：[usestrix/strix](https://github.com/usestrix/strix)（Apache License 2.0）
> 起因：[20260813.md](20260813.md)「GitHub趨勢／平台治理｜開源AI滲透測試agent Strix」該則新聞建議在隔離沙盒試用，導入前先做資安查核
> 評估日期：2026-08-13　評估版本：commit `8ca0c4a`（2026-08-12），對應 `pyproject.toml` 版本 1.5.3、預設沙盒映像 `ghcr.io/usestrix/strix-sandbox:1.3.0`
> 方法：shallow clone 原始碼實際檢視 Docker執行架構（`containers/Dockerfile`、`strix/runtime/docker_client.py`）、遙測路徑（`strix/telemetry/*.py`）、scope邊界控制程式碼（`strix/core/inputs.py`、`strix/agents/prompts/system_prompt.jinja`），非僅閱讀README

## 結論

Strix 的「工具本身」外洩面控制得不錯——遙測（PostHog/Scarf）程式碼實際讀取後與其 README 聲明一致，只送匿名聚合指標，不含掃描目標、程式碼或漏洞細節；但它的「攻擊行為邊界」目前**完全依賴 LLM system prompt 的文字指令自律，沒有任何網路層/程式碼層的技術性 allowlist 或防火牆去阻擋 agent 打到 scope 外的主機**——容器有完整對外連線能力且被授予 `NET_ADMIN`/`NET_RAW`（供 nmap 用），一旦目標網站對 agent 做提示注入（prompt injection）誘導其擴大攻擊範圍，沒有底層機制能攔截。加上這是一支會**實際執行攻擊利用（RCE/SQLi/SSRF等）**的雙重用途工具，其風險重心不在「會不會偷資料」而在「使用規範與人為 scope 圈定夠不夠嚴謹」。**建議結論：可在完全隔離的沙盒環境（獨立網路命名空間、僅能連到公司自建的靶機/staging，禁止對外連網）試用評估，且僅限對自有系統測試；在取得技術性網路層 scope 限制或人工二次覆核機制前，不建議讓它在能連到正式內部網路或任何未經明確書面授權的第三方目標上運作。**

## 二、風險項目

### 高：攻擊範圍／scope 控制完全依賴 LLM 自律，無技術性強制
實際讀 `strix/core/inputs.py::build_scope_context()`，其產出的 `authorized_targets`／`user_instructions_do_not_expand_scope` 只被塞進 `system_prompt_context`（`strix/core/runner.py:285-322`），最終渲染進 `strix/agents/prompts/system_prompt.jinja` 的一段純文字指示（第61-106行，例如「NEVER test any external domain... that is not explicitly listed」）。這代表 scope 邊界**只是喂給 LLM 的一段話**，沒有對應的網路層 egress 防火牆、iptables 規則或 DNS/IP allowlist 去實際攔截容器對外連線。容器本身（`strix/runtime/docker_client.py`）具備完整對外網路能力並被加上 `NET_ADMIN`/`NET_RAW`（供 nmap SYN scan 用），若目標系統含有提示注入（prompt injection）內容，或 LLM 因幻覺誤解使用者輸入，理論上可能主動連線/攻擊 scope 外主機，而系統層面沒有硬性阻擋。
唯一發現的「程式化 allowlist/denylist」是 `strix/tools/proxy/caido_api.py` 裡的 `scope_rules()`/`scope_create()`——但這是 Caido 代理**本身的 scope 設定 API**，屬於 agent「可自行選擇呼叫」的工具，並非掃描啟動時系統強制建立、鎖死到使用者指定目標的防護。

### 中：容器擁有 `NET_ADMIN`/`NET_RAW` + `sudo NOPASSWD` 的 root 等級能力
`containers/Dockerfile` 建立的 `pentester` 使用者被加入 `sudo` 群組並設 `NOPASSWD:ALL`（`echo "pentester ALL=(ALL) NOPASSWD:ALL" >> /etc/sudoers`），加上 `docker_client.py` 注入的 `NET_ADMIN`/`NET_RAW`。這些是執行 nmap/滲透工具「必要」的能力，非過度授權，但意味著萬一 agent 執行了惡意/失控指令，容器內幾乎沒有最小權限邊界可言（等同容器內 root）。因容器本身未加 `--privileged` 也未掛 docker.sock，逃逸到 host 的路徑目前未發現，風險侷限在容器內，但仍建議搭配 `STRIX_SANDBOX_MEM_LIMIT`/`STRIX_SANDBOX_CPUS`/`STRIX_SANDBOX_PIDS_LIMIT`（見 `docker_client.py` 的 `_apply_resource_limits`）等資源上限與獨立網路命名空間使用。

### 中：一行 curl\|bash 安裝、發布流程未見 checksum／簽章驗證
`README.md` 第82行：`curl -sSL https://strix.ai/install | bash`，對應 `scripts/install.sh` 會呼叫 GitHub Releases API 抓最新版本號，再用 `curl` 下載對應平台的 tarball/zip 並直接解壓覆蓋安裝，過程中**未見任何 sha256sum 校驗或 GPG/cosign 簽章驗證**；檢視 `.github/workflows/build-release.yml` 也沒有找到產生 checksum 或簽章的步驟。沙盒映像同樣是用 tag（`ghcr.io/usestrix/strix-sandbox:1.3.0`）而非 digest 釘選，`docker_client.py:179-181` 的 `image_exists`/`images.pull` 邏輯也未做 digest 或簽章比對，供應鏈完整性依賴「相信 GHCR 帳號沒被盜用／CI 沒被污染」的信任假設，缺乏額外技術性驗證層。

### 中：無 `SECURITY.md`，漏洞通報流程未制度化
repo 根目錄與 `.github/` 下皆未找到 `SECURITY.md`，僅有一般的 `bug_report.md`/`feature_request.md` issue 模板。這意味著若試用中發現 Strix 本身的漏洞，沒有官方指定的私下通報管道（如 `security@` 信箱或 GitHub Security Advisories 說明），只能走一般 issue 或社群 Discord，對企業內部而言通報/修補時效不明。

### 低：可選第三方資料流——第三方 Web 搜尋 API 與雲端版
若操作者設定 `PERPLEXITY_API_KEY`（`strix/tools/proxy` 之外的 `strix/tools/web_search/tool.py`），agent 產生的搜尋查詢字串（可能包含目標技術棧、CVE編號等由 LLM 自行組合的內容）會送到 `https://api.perplexity.ai`，屬於使用者自行選配、非預設開啟、也非 usestrix 自家伺服器，但仍是額外的第三方外流路徑，公司試用時應留意是否要停用（不設定該環境變數即可）。另外，若選用官方雲端版 app.usestrix.com 而非自架 CLI，則掃描目標與LLM互動預設會經過 usestrix 平台代管，此評估僅涵蓋開源自架 CLI 路徑，雲端版需另評估。

### 低：依賴套件版本抽查未見明顯過期／已知高危 CVE
抽查 `uv.lock` 關鍵套件：`cryptography 48.0.1`、`docker 7.1.0`、`litellm 1.90.1`、`openai-agents 0.19.0`、`requests 2.34.2`、`pypdf 6.14.2`，版本皆屬近期釋出，未發現明顯停滯在已知高危CVE版本上的套件。惟本次未逐一比對 CVE 資料庫做窮盡查核，屬淺層抽查，非完整 SCA 掃描結果。

## 三、建議的安裝與使用方式

1. **獨立實體/虛擬機或雲端沙盒**，不要在能連到公司正式內網（VPN/內部DNS/內部服務段）的機器上安裝 CLI 或跑容器。
2. **網路層強制隔離**：用 `STRIX_DOCKER_SANDBOX_NETWORK` 環境變數（`strix/runtime/docker_client.py` 的 `_apply_sandbox_network`）把沙盒容器綁到一個自訂 Docker network，該 network 只路由到公司自建的靶機/測試環境，對外（含公司內網其餘網段與網際網路）一律阻斷——不要依賴 Strix 自身的 prompt-level scope 宣告。
3. 掃描標的僅限**公司自有、已取得書面測試授權的系統**（如自架的 DVWA/juice-shop 或自建的 staging 環境），絕不指向任何第三方網域、雲端服務或未授權主機。
4. 設定資源上限：`STRIX_SANDBOX_MEM_LIMIT`、`STRIX_SANDBOX_CPUS`、`STRIX_SANDBOX_PIDS_LIMIT`，避免失控程序耗盡宿主機資源。
5. 若無需雲端報告寄送功能，不必操作 viewer 的「email report」流程；若要試用，僅用測試用信箱，理解該功能會把加密PDF（不含密碼）送到 `app.strix.ai`。
6. 除非要用第三方情資查詢功能，否則不要設定 `PERPLEXITY_API_KEY`，避免額外外流路徑。
7. 安裝時建議改用「先下載 release tarball、人工核對 GitHub Release 頁面上的 SHA 或自行重新建置」的方式，避免直接執行 `curl \| bash`；至少要先讀過 `scripts/install.sh` 內容（本次已讀，未發現額外惡意行為）。
8. LLM API key（`LLM_API_KEY`）建議使用測試專用、可隨時撤銷、額度受限的 key，不要用正式營運 key。

## 四、PoC 的環境要求

- PoC 攻擊利用程式碼與掃描報告預設寫在本機執行目錄下的 `./strix_runs/<run_name>/`（`strix/core/paths.py` 的 `RUNS_DIR_NAME`），為一般檔案系統權限，非額外加密儲存；本次查證未發現有任何路徑會把這個目錄的內容自動上傳到外部（僅使用者主動觸發 viewer 的「寄送報告」功能才會外傳，且是加密PDF）。
- 因此使用單位須自行確保 `strix_runs/` 目錄的檔案權限與存取控制（例如不要放在共享/雲端同步資料夾中），並在評估結束後清除其中可能含有的漏洞細節、憑證、內部路徑等敏感資訊。
- PoC 執行環境本身必須僅限自有系統：容器擁有 `NET_ADMIN`/`NET_RAW` 與容器內 `sudo NOPASSWD`，若目標環境有其他服務或連往公司內網，存在被 agent「順手」波及的風險（見上方高風險項）。
- 沙盒隔離要求：獨立 Docker network、限制對外連線僅能到指定靶機、資源配額（CPU/記憶體/PID）上限、執行完畢後整個容器與 `strix_runs/` 內容應視為含敏感資訊而妥善銷毀或加密保存。
- 禁止在同一沙盒中放置任何非測試授權範圍的系統或帳密（含公司內部SSO、雲端服務憑證等），因為 agent 執行環境內建 gitleaks/trufflehog 等憑證掃描工具，會主動搜尋並可能寫入報告中。

## 五、給決策者的一句話

Strix 工具本身的資料外洩控制做得比預期嚴謹（遙測程式碼與其隱私聲明一致），但它是一支會實際發動攻擊的雙重用途工具，且「不打到 scope 外」目前只靠寫在 prompt 裡的一句話而非技術性網路管制，因此可評估但務必用網路層隔離把它關進只能碰自家靶機的沙盒，而不是信任它自己會守規矩。
