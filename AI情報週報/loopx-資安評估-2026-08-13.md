# LoopX 資安評估

> 對象：[huangruiteng/loopx](https://github.com/huangruiteng/loopx)（MIT License）
> 起因：[20260813.md](20260813.md)「GitHub趨勢｜LoopX狀態核心」該則新聞建議評估其中斷恢復機制，導入前先做資安查核
> 評估日期：2026-08-13　評估版本：`80e844f`（main，shallow clone；pyproject 版本號 0.4.5）
> 方法：shallow clone 原始碼實際檢視狀態持久化儲存方式、交接存取控制機制、遙測路徑，非僅閱讀README

## 結論

LoopX 的狀態持久化是「本機純文字 JSON + fcntl 檔案鎖」，沒有任何加密；其內建的 HTTP 狀態伺服器（`loopx serve-status`）預設綁定 127.0.0.1 且無驗證機制，但 `--host` 參數可被使用者自行改成 `0.0.0.0`，一旦改動即在無任何 token/密碼驗證下對區網開放讀寫（含 reward/quota/todo 寫入 API）。安裝管道是標準 curl\|bash 抓取 GitHub 原始碼 tar 包，僅計算下載後的自我 SHA256（非獨立簽章/攻擊者可控），與另外存在、有 checksum+attestation 的正式 release 產物是兩條不同、未合併的路徑。核心套件本身零執行期依賴、CI/測試（267 個測試檔）與 SECURITY.md 齊備，未發現任何遙測/回傳到 huangruiteng 或第三方伺服器的程式碼。**建議結論：可在隔離測試機、預設本機綁定、不對外開放埠口的條件下小範圍試裝評估，但暫不建議在正式專案或含真實憑證的環境中導入，也不建議把 --host 改為非 loopback 值。**

## 一、查證通過的項目

| 項目 | 查證結果 |
|---|---|
| 無遙測/回傳第三方伺服器 | 全庫 grep `telemetry`/`analytics`/`posthog`/`sentry` 等關鍵字，命中皆為內部術語（如 LLM provider call 計數、reward memory 的內部 telemetry 欄位），未發現任何送資料到 huangruiteng 或第三方端點的程式碼；唯一對外網路呼叫是 GitHub（`self_update.py`、`install_contract.py`）與使用者自行設定的 model provider（如 `doubao_model_behavior_actor.py` 呼叫 volces.com，屬使用者自主設定的 LLM endpoint，非隱性回傳）。 |
| 核心套件零執行期依賴 | `pyproject.toml`：`dependencies = []`，只有 `test` extra（pytest/ruff/mypy 等），供應鏈攻擊面小。 |
| 密鑰/憑證處理 | 未發現讀取或落地儲存真實 LLM API key 內容的程式碼；`quota.py`、benchmark adapters 只引用環境變數「名稱」（如 `OPENAI_API_KEY`），並在多處（`content_ops/surface.py`、`issue_fix/feasibility.py`、`explore/trace_runtime.py` 等）主動偵測並拒絕含 `bearer `/`secret`/`api_key` 樣式字串寫入狀態，屬防禦性設計。 |
| 正式 release 有 checksum + attestation | `.github/workflows/release-artifacts.yml`：`release_artifacts.py write-checksums`/`verify-checksums` 產生 `SHA256SUMS`，並有「Attest release packages」步驟。 |
| SECURITY.md / 治理文件齊備 | `SECURITY.md` 要求走 GitHub Private Vulnerability Reporting；`GOVERNANCE.md` 明確記錄唯一維護者 `@huangruiteng`（自 2026-05-31）與決策流程。 |
| 測試覆蓋規模 | `tests/` 下 267 個測試檔，CI（`python-tests.yml`）含 ruff lint + pytest，push/PR 皆觸發。 |
| Windows 相容性明確聲明 | `file_lock.py` 對 `fcntl` 不可用時有 fallback 分支且標註 `pragma: no cover`，非隱藏地跳過鎖定，行為透明。 |

## 二、風險項目

### 高：狀態資料儲存與交接完全無存取控制，`--host` 可被改為對外開放

`loopx/paths.py` 顯示狀態根目錄預設為 `~/.codex/loopx/registry.global.json`，專案層為 `<project>/.loopx/registry.json`，皆是明碼 JSON，**沒有任何加密**。並發控制靠 `loopx/file_lock.py` 的 `fcntl` 檔案鎖，鎖的持有者身分（`agent_id`）是從環境變數 `LOOPX_AGENT_ID` 自報（`_identity()` 函式），**沒有身分驗證**——任何能在同一台機器起一個行程並設定該環境變數的人/agent，都能宣稱自己是任意 agent 並取得/釋放鎖，交接記錄可被偽造。

更關鍵的是 `loopx/status_server.py`（`loopx serve-status` 對應的 HTTP 伺服器）：
- 預設 `DEFAULT_STATUS_HOST = "127.0.0.1"`，且原始碼註解自陳「Return CORS headers for an unauthenticated response」（第107行）——這條服務**設計上就沒有驗證機制**，安全性完全依賴綁定位址。
- `loopx/cli_commands/support_control.py:408`：`serve_status_parser.add_argument("--host", default=DEFAULT_STATUS_HOST, help="Bind host. Defaults to localhost only.")`——`--host` 可由使用者自由覆寫。
- CORS 檢查（`is_loopback_origin`）只防護「瀏覽器讀取跨源回應」，對非瀏覽器的 HTTP client（curl、其他 agent、內網掃描工具）完全不設防；一旦 `--host 0.0.0.0`，`/reward/append`、`/control-plane/configure-goal/apply` 等寫入端點會在**零驗證**下對整個網段開放，任何人可竄改目標（goal）、關卡（quota/self_repair 設定）、reward/todo 狀態。

對照題目關切的「可驗證交接」機制：目前 LoopX 的交接（handoff）建立在「本機檔案鎖 + 自報 agent_id」之上，沒有任何身分驗證、簽章或權杖，安全邊界完全等同於「誰能碰到這台機器的檔案系統/這個埠口」。

### 中：一行安裝（curl\|bash）沒有獨立簽章驗證，與有 checksum 的正式 release 是兩條不同管線

`loopx/install_contract.py` 的 `NO_CLONE_INSTALL_URL = "https://huangruiteng.github.io/loopx/install.sh"`，`loopx/self_update.py::_command_for_source()` 產生的安裝/更新指令固定是：

```
curl -fsSL https://huangruiteng.github.io/loopx/install.sh | bash
```

實際下載腳本 `scripts/install-from-github.sh` 的流程是：呼叫 GitHub commits API 解析 ref 對應的 40 碼 commit SHA → 從 `codeload.github.com` 下載該 commit 的 tar.gz → **自行計算**下載檔案的 SHA256 並記錄到 release manifest（`archive_sha256`）。這個雜湊只是「事後自證」，沒有對照任何獨立發布、可信第三方簽署的 checksum 或 GPG 簽章——如果 GitHub 帳號或 repo 遭挾持，這條鏈路無法偵測。相對地，`release-artifacts.yml` 有 `write-checksums`/`verify-checksums` 產生 `SHA256SUMS` 並有 attestation 步驟，但這是**走正式 GitHub Release 產物**的另一條路徑，與預設「一行安裝」使用的 repo 原始碼歸檔（codeload archive）**並非同一份、也未互相驗證**。使用者若照 README 建議的一行安裝，實際上繞過了有 checksum 保護的 release 產物。

### 低：單一維護者，專案僅存在約 2.5 個月

`GOVERNANCE.md`／`AUTHORS.md` 顯示專案自 2026-05-31 開始公開、`@huangruiteng` 是唯一的「Creator and lead maintainer」且對安全處理有最終決定權，屬於典型 bus-factor=1 的早期專案；`SECURITY.md` 回應時間承諾為 5 個工作天內確認，屬合理但無 SLA 保證。專案迭代速度快（大量 capability 目錄、267 個測試檔），代表活躍開發，但也意味著介面/狀態結構可能尚未穩定。

## 三、建議的安裝與使用方式

1. 在獨立、非正式專案的隔離帳號/VM 或容器內試裝，不與正式專案共用 `~/.codex/loopx` 執行期根目錄（可用 `LOOPX_REGISTRY`/`common_runtime_root` 覆寫路徑做隔離）。
2. 安裝前先 `curl -fsSL https://huangruiteng.github.io/loopx/install.sh -o install.sh`，人工檢視腳本內容後再 `bash install.sh`，不要盲目 `curl | bash`（本評估已檢視過對應的 `scripts/install-from-github.sh`/`scripts/install-local.sh`，內容與上述分析一致，但每次更新都應重新檢查）。
3. **絕對不要**對 `loopx serve-status` 下 `--host 0.0.0.0` 或任何非 loopback 位址；若真需要跨機存取，應自行在其前面加一層有驗證的反向代理（如 nginx + basic auth 或 mTLS），不要依賴 LoopX 內建的 CORS 檢查作為安全邊界。
4. 不要把公司內部真實 LLM API 金鑰以外的敏感專案內容（客戶資料、內部程式碼片段）交給尚在快速迭代、缺乏獨立簽章的工具做「長任務摘要持久化」，先以無敏感內容的 sandbox 專案試跑。
5. 多 agent 交接情境下，若同機存在其他不受信任的行程，應假設 `LOOPX_AGENT_ID` 可被偽造，不要把它當成身分驗證依據。

## 四、PoC 的環境要求

- Python 3.11+（`pyproject.toml` 要求 `requires-python = ">=3.11"`），Linux/macOS 為主（`fcntl` 鎖機制依賴 POSIX；Windows 上鎖定會走無鎖 fallback，多 agent 併發寫入的一致性保證會減弱，不建議在 Windows 上做多 agent 併發 PoC）。
- 需要一個獨立的測試專案目錄（非正式 repo），並確認 `~/.codex/loopx` 或以 `LOOPX_REGISTRY` 指定的路徑不會與其他工具衝突。
- 若要測試 `serve-status`，僅在 127.0.0.1 上驗證，且事先確認防火牆/安全群組沒有把該埠口對外開放。
- 需要 GitHub 網路存取權（安裝腳本會呼叫 GitHub commits API 與 codeload.github.com）。

## 五、給決策者的一句話

LoopX 的狀態持久化與交接機制目前完全建立在「本機檔案系統的存取權」之上、沒有加密也沒有身分驗證，可以在隔離沙盒中小範圍試裝評估其中斷恢復體驗，但在有正式存取控制要求或會綁定非 loopback 埠口的情境下暫不建議導入。
