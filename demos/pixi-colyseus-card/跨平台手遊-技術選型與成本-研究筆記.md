## 一句話結論

Godot 內建一套四層的多人連線框架。用同一個專案就能做出玩家端，以及不需要螢幕的專用伺服器，適合小房間即時對戰。
若遊戲需要帳號、金流、排行榜或大量同時在線，業界常見做法是 **Godot 只做玩家端**，伺服器改用 Nakama、Colyseus 或自建後端。
如果是 2D 遊戲，又要同時推出網頁版和 App，前端也可以改用 **PixiJS**（見第十一節）。網頁技術路線的完整比較（PixiJS／Phaser／Three.js + Capacitor，以及 React Native／Expo）見第十二節，開發費用見第十三節，非人力成本（含 Phaser 費用、引擎授權、各階段支出）見第十四節。

## 一、整體架構：四層

```
┌─────────────────────────────────────────────┐
│ 4. 遊戲邏輯層    @rpc 函式（遠端呼叫）        │  ← 自己寫的程式
├─────────────────────────────────────────────┤
│ 3. 場景複製層    MultiplayerSpawner           │  ← 自動同步「物件生成／刪除」
│                  MultiplayerSynchronizer      │  ← 自動同步「屬性數值」
├─────────────────────────────────────────────┤
│ 2. 多人 API 層   SceneMultiplayer             │  ← 身分驗證、訊息轉送、RPC 路由
├─────────────────────────────────────────────┤
│ 1. 傳輸層        ENet / WebSocket / WebRTC    │  ← 實際收發封包
└─────────────────────────────────────────────┘
```

每一層都能獨立替換。例如傳輸層從 ENet 換成 WebSocket，上面三層的程式碼不必修改。

## 二、第 1 層：傳輸層（MultiplayerPeer）

| 傳輸方式 | 底層協定 | 支援平台 | 適合用途 |
|---|---|---|---|
| **ENetMultiplayerPeer**（預設） | UDP（速度快，但封包可能遺失） | PC、iOS、Android | 即時對戰首選，同一條連線可分成「必達」與「不保證送達」兩種頻道 |
| **WebSocketMultiplayerPeer** | TCP（較慢，但保證送達） | 全平台，**包含網頁版** | 網頁版只能用這個；回合制、卡牌類遊戲也適用 |
| **WebRTCMultiplayerPeer** | 玩家之間直接連線 | 網頁版內建；**PC 與手機需另裝 GDExtension 外掛** | 點對點連線，可省下伺服器成本 |

手機與網頁版的注意事項（官方文件）：

- Android 匯出時必須勾選 `INTERNET` 權限，否則無法連網。
- 網頁版不能用 ENet，因為瀏覽器不開放 UDP。

建立連線的程式碼（官方文件）：

```gdscript
# 伺服器端
var peer = ENetMultiplayerPeer.new()
peer.create_server(PORT, MAX_CLIENTS)
multiplayer.multiplayer_peer = peer

# 玩家端
var peer = ENetMultiplayerPeer.new()
peer.create_client(IP_ADDRESS, PORT)
multiplayer.multiplayer_peer = peer
```

## 三、第 2 層：SceneMultiplayer（連線管理）

這一層負責管理「誰連進來、誰可以傳訊息」。以下設定項目出自官方類別文件：

| 設定或方法 | 白話說明 | 預設值 |
|---|---|---|
| `auth_callback` + `send_auth` / `complete_auth` | 入場驗證：連線後先確認身分，通過才算正式加入 | 未設定時，任何人一連上就直接放行 |
| `auth_timeout` | 超過這個時間還沒完成驗證就斷線 | 3 秒 |
| `server_relay` | 由伺服器替玩家之間轉送訊息 | 開啟 |
| `refuse_new_connections` | 拒絕所有新連線 | 關閉 |
| `allow_object_decoding` | 允許透過網路傳送「物件」 | 關閉（官方警告有資安風險，不要開） |
| `max_sync_packet_size` | 同步封包的大小上限 | 1350 bytes |
| `max_delta_packet_size` | 增量封包（只送變動部分）的大小上限 | 65535 bytes |

身分編號規則：

- 伺服器的編號固定為 **1**，玩家連線後會拿到一個隨機的正整數編號。
- `multiplayer.is_server()`：判斷自己是不是伺服器。
- `multiplayer.get_unique_id()`：取得自己的編號。
- `multiplayer.get_remote_sender_id()`：在 RPC 函式中查出呼叫者是誰。

連線事件（signal）：`peer_connected`、`peer_disconnected`、`connected_to_server`、`connection_failed`、`server_disconnected`。

## 四、第 3 層：自動同步節點

### MultiplayerSpawner：同步物件的生成與刪除

伺服器生成一隻怪物，所有玩家的畫面上也會自動出現；伺服器刪除它，其他人那邊也會跟著消失。開發者只需要事先登記「哪些場景可以被生成」。

### MultiplayerSynchronizer：同步數值

例如角色的位置與血量。每個要同步的屬性可以選擇三種模式（`SceneReplicationConfig.ReplicationMode`）：

| 模式 | 行為 | 適合的資料 |
|---|---|---|
| `REPLICATION_MODE_ALWAYS` | 持續傳送，使用不保證送達的方式 | 位置、旋轉這類一直在變的數值 |
| `REPLICATION_MODE_ON_CHANGE` | 數值改變時才傳送，使用保證送達的方式 | 血量、分數、狀態 |
| `REPLICATION_MODE_NEVER` | 不同步 | 只有本機需要的資料 |

其他重點：

- `replication_interval` 與 `delta_interval` 用來控制同步頻率，預設為 0，代表每一幀都同步。
- 可見度過濾（`set_visibility_for`、`add_visibility_filter`）可以指定「這筆資料只送給某些玩家」。例如對手的手牌不送給其他人，**資料根本不會傳出去**，比只在畫面上隱藏安全得多。
- 同步方向只能從權威端（authority，有最終決定權的一方，預設是伺服器）送往其他端。
- 不支援同步 Resource 這類物件型別的屬性。舊方法 `property_set_sync` 與 `property_set_watch` 已棄用，改用 `property_set_replication_mode`。

## 五、第 4 層：RPC（遠端呼叫函式）

RPC 的意思是：在這台機器呼叫某個函式，實際上由另一台機器執行。

```gdscript
@rpc("any_peer", "call_local", "reliable", 0)
func request_move(dir: Vector2):
    # 伺服器端務必檢查：是誰送來的？這個動作是否合法？
    pass
```

| 參數 | 選項 | 意思 |
|---|---|---|
| 誰能呼叫 | `authority`（預設）／`any_peer` | 只有權威端可以呼叫／任何玩家都可以呼叫 |
| 在哪執行 | `call_remote`（預設）／`call_local` | 只在對方機器執行／自己這邊也執行一次 |
| 可靠度 | `reliable`／`unreliable`／`unreliable_ordered` | 保證送達／可能遺失／可能遺失但順序不會亂 |
| 頻道 | 數字（預設 0） | 分開不同頻道，避免互相塞車 |

### 重要的架構限制

官方文件寫明：伺服器與玩家端的 RPC 必須在**函式名稱、`@rpc` 設定、場景節點路徑**三方面完全一致。引擎會用一組總檢查碼比對，不一致時跳出的錯誤訊息往往與真正原因無關，很難除錯。函式的參數內容則不會被檢查。

> **推論**：因為有上述限制，伺服器和玩家端實務上幾乎一定放在同一個專案裡。
>
> - 優點：程式碼共用，AI agent 也只需要讀一個專案。
> - 缺點：伺服器邏輯很容易一起被打包進玩家的 App，而 GDScript 有公開工具可以還原原始碼。
>
> **已實測（Godot 4.7.2，見第十五節第 2 項）**：
>
> - 玩家版預設**會**把伺服器腳本一起打包進去。
> - 在玩家版的匯出設定加上 `exclude_filter="server/*"` 後，伺服器腳本就被排除，玩家版照樣能正常連線遊玩。
> - 前提是伺服器腳本只能在執行時用 `load()` 載入，不能用 `preload`。

## 六、三種連線架構

| 架構 | 說明 | 優點 | 缺點 |
|---|---|---|---|
| **主機玩家**（listen server） | 由其中一位玩家兼任伺服器 | 不需要租伺服器 | 主機玩家能作弊；主機斷線整場結束；手機當主機耗電又不穩定 |
| **專用伺服器**（dedicated server） | 匯出無畫面版本，放在雲端主機執行 | 伺服器擁有最終決定權，最能防作弊 | 需要負擔主機費用並自行維運 |
| **點對點**（WebRTC mesh） | 玩家之間直接連線 | 省成本 | 難防作弊；行動網路經常連不通 |

專用伺服器的做法（官方文件）：

- 匯出設定的 Resources 分頁選擇「Export as dedicated server」，或執行時加上 `--headless` 參數。
- 這樣就不需要顯示卡與螢幕，可以在 Linux 雲端主機上執行。
- 匯出時會自動加上 `dedicated_server` 標籤，程式中可用 `OS.has_feature("dedicated_server")` 判斷目前是否為伺服器版。

## 七、延遲補償：netfox 外掛

Godot 內建的同步功能**沒有延遲補償**。手機網路延遲 50～200 毫秒很常見，沒有補償時，玩家按下按鈕後角色會慢半拍才動。社群主流的解法是 **netfox**：

| 功能 | 白話說明 |
|---|---|
| 統一時鐘 | 讓所有機器對齊同一個遊戲時間 |
| 玩家端預測與回滾（RollbackSynchronizer） | 玩家端先假設動作成功並立刻顯示；伺服器結果回來後若不同，就悄悄修正 |
| 平滑補間（TickInterpolator） | 讓其他玩家的角色移動看起來順暢 |
| netfox.noray | 協助穿透家用網路與行動網路的阻擋（NAT 穿透），連不通時改走中繼伺服器 |
| netfox.extras | 提供連網武器、支援回滾的輸入處理等現成元件 |

netfox 以「伺服器說了算，玩家只送操作指令」為設計前提，同時兼顧防作弊。官方範例遊戲是 Forest Brawl。

**與 Godot 4.7 的相容性（已實測，見第十五節第 3 項）**：

- 官方 README 只寫「支援 Godot 4.x」，但自動測試只在 4.2.2 上跑。
- 實際在 4.7.2 上跑完整測試套件：333 項中有 5 項失敗。
- 查過原始碼後，失敗原因是**測試本身寫錯**，不是 netfox 在 4.7 上壞掉。

## 八、另一條路：Godot 只做玩家端，伺服器另外實作

| 方案 | 伺服器語言 | 同步方式 | 適合情境 |
|---|---|---|---|
| **Godot 內建** | GDScript / C# | 屬性同步加 RPC | 小房間即時對戰 |
| **Nakama** | Go（需要 CockroachDB 資料庫） | RPC 加伺服器端寫入 | 帳號、聊天、配對、排行榜、社交功能一次備齊 |
| **Colyseus** | TypeScript / Node.js | 只傳送變動部分的二進位資料 | 團隊熟悉 Node.js，想把房間邏輯寫成程式碼 |
| **自建後端**（Go、Node、Java 等） | 任意 | WebSocket 或 HTTP | 已經有後端團隊與既有的會員、金流系統 |

Nakama 與 Colyseus 都有官方的 Godot 套件，支援 iOS 與 Android（第三方來源與官方套件頁面）。

## 九、依遊戲類型的建議（推論）

| 遊戲類型 | 建議架構 |
|---|---|
| 回合制、卡牌、休閒、涉及金流或點數 | Godot 只做玩家端，搭配自建後端或 Nakama，以 WebSocket 連線；所有結果由伺服器計算，玩家端只負責顯示 |
| 小房間即時對戰（2～16 人） | Godot 專用伺服器搭配 ENet 與 netfox |
| 大量同時在線（MMO 類） | 使用外部後端，Godot 內建框架不適合這種規模 |
| 派對遊戲、朋友連線 | 主機玩家模式或 WebRTC，搭配 noray 處理連線穿透 |

## 十、資安檢查清單

1. 永遠不要相信玩家端送來的資料。位置、計時、金額、抽獎結果都要由伺服器計算或驗證（官方文件也強調這點）。
2. 標記為 `any_peer` 的 RPC 是對外開放的入口，每一支都要檢查 `get_remote_sender_id()` 與參數內容。
3. 設定 `auth_callback`，不要讓任何人一連上就直接放行。
4. 專用伺服器若不需要玩家之間互傳訊息，考慮關閉 `server_relay`。
5. `allow_object_decoding` 保持關閉。
6. 伺服器專用的程式碼不要打包進玩家的 App。

## 十一、前端改用 PixiJS 的比較

> 本節假設「pixle」指的是 **PixiJS**，也就是網頁用的 2D 繪圖引擎。版本已用 npm 查證：最新版是 **8.22.0（2026-10-01）**。

### PixiJS 是什麼

- PixiJS 官方文件自稱是「**2D 繪圖引擎**」，不是遊戲引擎。它只負責把圖畫到畫面上，速度很快。
- **它沒有內建**：物理、場景編輯器、網路連線。音效要另外裝官方套件 `pixi.sound`。
- 繪圖方式會自動挑選：優先用 WebGPU（新一代瀏覽器繪圖介面），不支援時退回 WebGL，再不行用 Canvas。
- 官方文件只提到可以搭配 Tauri、Electron 做成桌面或行動 App。**做手機 App 要另外用 Capacitor 這類工具把網頁包成 App**（推論：社群常見做法，官方文件沒有提）。

### 架構上的根本差異

```
Godot 架構：
  Godot 玩家端 ──(Godot 內建多人框架：ENet / WebSocket)── Godot 專用伺服器
  （伺服器與玩家端通常是同一個專案）

PixiJS 架構：
  PixiJS 繪圖 + TypeScript 遊戲邏輯
        │  (WebSocket)
        ▼
  外部伺服器：Colyseus / Nakama / 自建後端
  （玩家端與伺服器天生是兩個專案）
```

- **PixiJS 沒有任何網路框架**，所以一定要搭配外部伺服器。
- 這反而會**自然形成「伺服器說了算、玩家端只負責顯示」的架構**，伺服器程式碼不會被打包進玩家的 App。第五節提到的 Godot「同專案」風險在這裡不存在。（推論）
- **Colyseus 和 PixiJS 都用 TypeScript**：前後端可以共用資料型別的定義。Colyseus 官方也有多個 PixiJS 範例，例如 MMO Demo 和回合制坦克 Demo（第三方來源）。

### 逐項比較

| 比較項目 | Godot（玩家端） | PixiJS（玩家端） |
|---|---|---|
| 定位 | 完整遊戲引擎 | 2D 繪圖引擎，其他功能要自己組 |
| 程式語言 | GDScript / C# | JavaScript / TypeScript |
| 視覺編輯器 | 有，可以拖拉場景 | 沒有，畫面全靠寫程式 |
| 內建網路 | 有，第一到第五節介紹的四層框架 | 沒有，要自己接 WebSocket、Colyseus 或 Nakama |
| 2D／3D | 兩者都支援 | 只有 2D |
| 手機 App | 原生匯出 iOS／Android | 用 Capacitor 等工具把網頁包成 App，實際在手機的瀏覽器元件（WebView）裡執行 |
| 網頁版 | 可以匯出，但有限制：**C# 專案不能匯出網頁版**（官方文件）；4.3 起改用單執行緒匯出，iOS Safari 相容性變好，代價是效能較差 | **網頁是它的主場**，載入快、檔案小 |
| 效能 | 原生程式，手機上較穩定 | 取決於手機的瀏覽器元件，舊款 Android 可能落差較大（查無公開的對照數據，見第十五節第 4 項） |
| Spine 骨骼動畫 | 官方 spine-godot：GDExtension 版不需重新編譯引擎；C# 版要用客製引擎，Spine 文件寫明手機與網頁目前還不支援 C# | 官方 spine-pixi-v8，由 Esoteric 與 PixiJS 團隊共同維護，需要 PixiJS 8.4.0 以上，支援 WebGPU |
| AI agent 好不好操作 | 要透過 MCP 外掛操作編輯器；場景檔是純文字，AI 讀得懂 | **全是程式碼，不需要 MCP**，AI 改完瀏覽器馬上看結果；JS/TS 也是 AI 學最多的語言（推論） |
| 原始碼保護 | GDScript 可被公開工具還原 | JavaScript 本來就看得到，必須做混淆（把程式碼打亂成看不懂） |
| 適合的團隊 | 遊戲背景、需要給企劃或美術用的編輯器 | 網頁前端背景 |

### 選型建議（推論）

| 情境 | 建議 |
|---|---|
| 2D 卡牌、休閒、博弈類，要同時出**網頁版和 App**，結果全由伺服器決定 | **PixiJS + Colyseus 或自建後端 + Capacitor** |
| 即時動作對戰、需要 3D、需要物理 | **Godot**（內建框架加 netfox） |
| 企劃或美術需要自己拖拉調整畫面 | **Godot**，PixiJS 沒有編輯器 |
| 主要用 AI agent 開發、想要最短的修改到驗證流程 | PixiJS 較直接；Godot 要多架一層 MCP |

**共同原則**：不論前端選哪個，涉及金額或結果的邏輯都必須放在伺服器。前端只負責顯示，而且一定能被破解者看到程式內容。

### 前端已經用 PixiJS，還需要 Godot 嗎？

**結論：大多數情況下不需要。** 伺服器直接用 TypeScript 寫，例如 Colyseus 或自建後端，比較合理。

Godot 在這套架構裡只剩一個角色可以當：「沒有畫面的伺服器」。但這樣做有三個問題：

| 問題 | 說明 |
|---|---|
| Godot 內建的多人連線功能用不上 | 自動同步和 RPC 的前提是**兩端都是 Godot**：雙方的函式名稱、設定、場景路徑都必須一致，還要通過檢查碼比對（官方文件，見第五節）。查不到 Godot 公開過這套連線格式的規格，也查不到 JavaScript 版的相容實作，所以 PixiJS 前端接不上（推論，未實際嘗試串接） |
| 剩下的只是一般的 WebSocket 伺服器 | Godot 的 WebSocket 可以和任何標準用戶端相容（官方文件），但通訊格式要自己設計。這件事用 Node.js 或 Go 做更簡單，人才也更多 |
| 前後端是不同語言 | 前端用 TypeScript，後端用 GDScript，資料格式和規則要寫兩份，容易對不上。用 Colyseus 的話，前後端都是 TypeScript，可以共用同一份定義 |

還值得用 Godot 的情況（推論）：

- **另一款遊戲**需要 3D、重度物理，或要在低階手機上跑原生 App。這是另一個專案的選型。
- 伺服器需要跑複雜的物理模擬。但前端如果要先自行預測結果，就得用 JavaScript 再寫一份完全一樣的物理規則，非常難做到。卡牌、博弈類通常用不到。
- 拿 Godot 編輯器當關卡編輯工具。可行但很少見，通常用 Tiled 這類地圖編輯器就夠了。

建議架構：

```
PixiJS 前端（網頁 + Capacitor 包成 App）
        │ WebSocket
        ▼
TypeScript 伺服器（Colyseus 或自建）→ 資料庫、金流、帳號
```


> **已實測**：上面這套組合（`@assetpack/core`、`pixi-filters` 除外）已經做成最小範例並實際跑過，21 項檢查全部通過。詳見第十五節第 5 項，範例專案在 [demos/pixi-colyseus-card](README.md)。

**和 Godot 相比少了什麼**：

- **視覺化編輯器**：只能靠 Tiled 拼地圖、Spine 做動畫，或 Figma 設計 UI 後用程式重建。
- **整合好的工作流程**：每個套件各自維護，版本升級時要自己確認彼此相容。
- **即時動作遊戲的延遲補償**：沒有 PixiJS 專屬的方案。Colyseus 0.18 的用戶端套件有內建 `Predict`／`Reconciler`，但沒有實測，成熟度還不能和 netfox 相比較。

**優勢**：

- 全部是網頁標準技術和 TypeScript，人才最多，AI agent 最熟悉。
- 網頁版和 App 版是同一份程式碼。
- 所有套件都免費。只有 Spine 要付費，而 Godot 路線同樣要付 Spine。

## 十二、網頁技術路線深入比較（PixiJS／Phaser／Three.js + Capacitor，或 React Native／Expo）

> 這條路線的做法：先做成網頁遊戲，再包成 App。AI 不需要 MCP 外掛來操作編輯器，直接改程式，瀏覽器馬上就能看結果。
> 下表的版本號全部用 `npm view` 查證（2026-10-07）。

### 版本現況

| 套件 | 最新版 | 定位 |
|---|---|---|
| PixiJS | 8.22.0 | 2D 繪圖引擎（只負責畫圖） |
| Phaser | 4.2.1（Phaser 4 在 2026-04 正式推出） | 完整的 2D 遊戲框架 |
| Three.js | 0.186.1 | 3D 繪圖函式庫 |
| Babylon.js | 9.29.0 | 完整的 3D 遊戲引擎（備選） |
| Capacitor | 8.5.2 | 把網頁包成 iOS／Android App |
| React Native / Expo | 0.87.1 / SDK 57 | 用 JavaScript 寫原生 App 的框架 |
| React Native Skia | 2.14.0 | React Native 上的 2D 繪圖元件 |
| expo-gl | 57.0.2 | 在 React Native 裡提供 WebGL 繪圖環境 |

### 第一層選擇：畫面用哪個引擎

| 比較項目 | **PixiJS** | **Phaser 4** | **Three.js** |
|---|---|---|---|
| 是什麼 | 2D 繪圖引擎 | 2D 遊戲框架 | 3D 繪圖函式庫 |
| 內建功能 | 只有畫圖、互動事件、資源載入；音效要另裝 `pixi.sound` | 場景管理、物理（Arcade 和 Matter 兩種）、鏡頭、地圖、輸入、音效全部內建 | 3D 場景、材質、燈光、模型載入；沒有物理和遊戲迴圈框架 |
| 繪圖技術 | WebGPU 優先，不支援時退回 WebGL，再退回 Canvas | 全新改寫的 WebGL 繪圖核心，官方說能妥善處理畫面資源被系統收回（context loss）的情況 | WebGL 為主，另有 WebGPU 繪圖器 |
| Spine 骨骼動畫 | 官方 spine-pixi-v8 | 社群或官方外掛（本次未查證） | 官方有 spine-threejs（本次未查證） |
| 自由度 | **最高**，架構完全自己決定 | 中等，要照 Phaser 的場景架構寫 | 高 |
| 開發速度 | 慢，基本功能要自己組 | **最快**，小遊戲一個晚上就能做出原型 | 3D 本來就慢 |
| AI agent 熟悉度 | 高（PixiJS 官方 GitHub 組織提供 pixijs-skills 技能包） | 高（官方另有 Game Agent MCP，見下方） | 高 |
| 適合 | 博弈、卡牌、老虎機這類**畫面效果多、遊戲規則由伺服器決定**的遊戲；或想自建引擎的團隊 | 動作、平台跳躍、益智這類**需要物理和關卡**的 2D 遊戲 | 3D 輕量遊戲、3D 展示 |

**PixiJS 和 Phaser 的差別，一句話說明**：PixiJS 給你一支很快的畫筆，Phaser 給你一整套遊戲製作工具箱。遊戲規則全部在伺服器、前端只負責「把結果演得漂亮」的話，PixiJS 的自由度更有優勢；遊戲規則在前端跑（例如物理碰撞）的話，Phaser 省事很多。

### 第二層選擇：怎麼變成 App

| 比較項目 | **Capacitor**（網頁包成 App） | **React Native / Expo**（原生 App 框架） |
|---|---|---|
| 原理 | 整個遊戲跑在手機內建的瀏覽器元件裡（iOS 用 WKWebView，Android 用 System WebView） | App 外殼是原生介面，遊戲畫面要另外用繪圖元件 |
| 遊戲引擎支援 | **PixiJS、Phaser、Three.js 都能直接用**，網頁版和 App 版是同一份程式碼 | **2026 年仍然沒有完整的 React Native 遊戲引擎**（第三方文章結論） |
| 2D 遊戲的做法 | 直接用網頁引擎 | 四種選擇各有缺陷，見下表 |
| 網頁版 | 原本就是網頁，零成本 | 要另外處理（Expo 有網頁支援，但遊戲繪圖元件不一定通用） |
| 適合 | **遊戲本體就是網頁遊戲** | App 主體是一般功能（會員、商城、社群），遊戲只是其中一部分 |

React Native 上做 2D 遊戲的四種選擇（整理自 2026-05 的第三方文章，數據是作者自己測的）：

| 選擇 | 狀況 | 效能數據 | 作者建議 |
|---|---|---|---|
| react-native-game-engine | 2020 年後就沒再更新 | 中階 Android 約 50 個物件就開始掉幀 | 只適合很簡單的益智遊戲或原型 |
| Phaser 4 放進 WebView | 可用，但跟 App 本體不共用資料 | Android WebView 上比桌機瀏覽器慢 5～10 倍 | 已經有現成的 Phaser 遊戲、要塞進 App 時才用 |
| expo-gl / react-native-wgpu | 只提供底層繪圖環境 | — | 要自己從零寫引擎才選 |
| **Skia + Reanimated 4** | 唯一走原生 GPU 的路線 | Galaxy A54：輕量負載 120fps、重負載 48fps；**低階 OPPO A16 約 300 個圖片，iPhone 12 mini 約 15,000 個** | 目標手機規格高於 OPPO A16 等級，而且願意自己補遊戲框架 |

> **PixiJS 放進 React Native**：有 `react-native-pixi` 這類套件，但不是主流做法。要用 PixiJS 的話，**直接用 Capacitor 比較合理**。

### AI agent 開發流程比較

| 比較項目 | 網頁路線（PixiJS／Phaser） | Godot 路線 |
|---|---|---|
| 改程式 | AI 直接改 TypeScript，不需要額外工具 | 改 GDScript 不需要額外工具；**改場景和節點**最好透過 MCP 外掛 |
| 看結果 | 開發伺服器存檔後自動重新整理。但 AI 要「看到」畫面，還是需要瀏覽器自動化工具：`chrome-devtools-mcp`（1.10.1）或 `@playwright/mcp`（0.0.83）都能截圖、讀 console 錯誤、模擬點擊 | 需要 Godot MCP 外掛，才能執行遊戲、截圖、模擬輸入 |
| 自動測試 | Playwright 這類網頁測試工具非常成熟 | 要靠 MCP 外掛或 Godot 的測試框架 |
| 官方 AI 服務 | **Phaser Game Agent MCP**（2026-07-08 推出）：一行指令就能接上 Claude Code、Cursor、Codex 等工具，自動產生程式、美術和音樂 | Godot 官方沒有 |

> **「不需要 MCP」要修正一下**：改程式確實不需要 MCP；但要讓 AI 自己驗證畫面對不對，還是要裝瀏覽器自動化的 MCP。差別在於這類工具很通用、很成熟，不像遊戲引擎的 MCP 外掛多半是社群自己做的。

**Phaser Game Agent MCP 的限制（官方頁面）**：
- 在 **Phaser 的雲端**執行，不是在你的電腦上跑。需要 Phaser 帳號，按建置時間收費（每分鐘 0.01 美元起），產生圖片和音樂另外計費。
- 匯出目標只列出網頁、Windows、macOS、Linux，**沒有手機版**，手機版還是要自己用 Capacitor 包。
- 程式碼和素材會上傳到外部雲端。公司專案使用前，要先確認資安與著作權政策。

### 網路連線

網頁路線的引擎**都沒有內建多人連線框架**，所以一律走第八節的「外部伺服器」模式：

```
PixiJS / Phaser / Three.js（瀏覽器或 Capacitor App）
        │ WebSocket
        ▼
Colyseus（TypeScript）/ Nakama / 自建後端
```

- 好處：前後端都可以用 TypeScript，資料型別定義可以共用。伺服器程式天生不會被打包進 App。
- 跟 Godot 內建框架比：沒有現成的「自動同步物件和屬性」功能，Colyseus 的狀態同步機制可以補上這一塊。

### App Store 上架風險（已查證 Apple 審核指南原文）

| 條款 | 內容 | 對網頁路線的影響 |
|---|---|---|
| **4.2 最低功能要求** | 「App 應該有超越『重新包裝的網站』的功能、內容與介面」 | 只是把網頁包一層殼，可能被退件。要加入像 App 的體驗，例如離線資源、原生推播、原生付款 |
| **4.7 小遊戲** | 允許 App 提供不在安裝檔內的「HTML5 和 JavaScript 小遊戲」，但開發者要為內容負責 | 主 App 內嵌多款 HTML5 小遊戲（平台型 App）是有明文依據的 |
| **2.5.2 下載可執行程式** | 不得下載、安裝或執行「會新增或改變 App 功能」的程式碼 | **熱更新（不經審核直接推送新程式碼）有風險**。只修 bug 一般被容忍；用熱更新上新功能，就違反這一條（推論，Apple 沒有明確界定） |
| **5.3.3 真錢遊戲** | 真錢博弈或彩票必須在使用地區取得執照、限定地區使用，而且 App 本身必須免費 | 跟技術路線無關，但博弈類必須符合 |

- Android 的審核寬鬆很多，但同樣有真錢博弈的地區限制。
- 熱更新工具已經很成熟，例如 `@capgo/capacitor-updater` 8.52.1。

### 總比較：Godot vs 網頁路線（PixiJS／Phaser）vs React Native

| 比較項目 | Godot | PixiJS + Capacitor | Phaser + Capacitor | React Native + Skia |

| 類型 | 完整遊戲引擎 | 繪圖引擎 | 2D 遊戲框架 | 原生 App 框架加繪圖元件 |
| 網頁版 | 可以（有限制） | **原生支援** | **原生支援** | 有限 |
| iOS／Android | 原生匯出 | WebView | WebView | 原生 |
| 低階 Android 效能 | **最好**（推論） | 取決於 WebView | 取決於 WebView（第三方：比桌機慢 5～10 倍） | 低階機約 300 個圖片（第三方） |
| 內建多人連線 | **有** | 無 | 無 | 無 |

## 十四、非人力成本分析：Phaser 費用、引擎授權、各階段支出

### 一句話結論

### 1. 最小範例：一台伺服器加兩到三個玩家端　✅ 通過

測試設計：
- 伺服器用 ENet。
- 入場驗證：密碼是 `letmein`。
- 用 MultiplayerSpawner 生成每位玩家的角色。
- 用兩個 MultiplayerSynchronizer 同步資料：一個公開（位置、血量），一個只給本人看（手牌）。
- 玩家端會故意送出三種作弊請求，看伺服器怎麼處理。

| 驗證項目 | 結果 |
|---|---|
| 入場驗證 | 密碼正確的 A、B 放行；密碼錯誤的 C 被拒絕，C 端收到 `peer_authentication_failed` |
| 角色生成同步 | A、B 都看到兩個角色，連續 8 次都穩定（另外刻意讓 B 晚 1 秒加入也一樣） |
| 合法移動 | 兩次各移動 5，伺服器上的位置從 100 變成 110，玩家端同步到相同數值 |
| 作弊：瞬移 9999 | 伺服器程式檢查後拒絕，位置沒有改變 |
| 作弊：玩家自己宣稱造成傷害 | 伺服器程式拒絕，血量維持 100 |
| 作弊：玩家呼叫只限伺服器的 `authority` RPC | **由引擎直接擋下**，錯誤訊息：`RPC 'server_only_announce' is not allowed ... Mode is "authority", authority is 1.` |
| 隱藏資料（手牌） | A 只看得到自己的手牌，B 的手牌在 A 這邊是空字串；B 那邊也一樣 |

**除錯紀錄**：第一輪測試時，後加入的玩家有時看不到先加入的玩家。查明原因是**測試腳本寫錯**：玩家端印完結果就立刻離線，伺服器照規則刪除它的角色並同步給其他人。改成「印完結果後保持連線，直到伺服器關閉」後，8 次全部通過。這不是 Godot 的問題。

### 2. 伺服器腳本能否從玩家版排除　✅ 可以，但要自己設定

| 匯出設定 | 匯出檔裡有沒有 `server/server_logic.gd` 的路徑 |
|---|---|
| 玩家版，沒有設定排除條件 | **有**（預設會把伺服器程式一起打包） |
| 玩家版，`exclude_filter="server/*"` | **沒有** |
| 專用伺服器版（dedicated_server） | 有 |

- 排除後的玩家版搭配伺服器版實際連線，跑 2 次都正常。伺服器端回報 `OS.has_feature("dedicated_server")` 為 true。
- 拿玩家版硬當伺服器啟動，會出現 `Attempt to open script 'res://server/server_logic.gd' resulted in error 'File not found'`，表示伺服器程式確實不在玩家版裡。
- 設計上的前提：伺服器腳本只能在執行時用 `load()` 載入。如果用 `preload`，玩家版會因為找不到檔案而無法啟動（推論，未另外測試）。
- 官方文件說明，dedicated server 匯出只會移除貼圖之類的畫面資源，**不會移除任何腳本**。要排除伺服器程式，只能靠匯出設定的排除條件。
- 附帶發現：`--export-pack` 只匯出 .pck 資源包，**不需要安裝 export templates**（匯出範本，正式打包 App 時才需要）。本機的 export_templates 資料夾是空的，照樣匯出成功。

### 3. netfox 與 Godot 4.7 的相容性　⚠️ 程式本身可用，但它的測試寫錯了

- 版本：netfox 主分支 commit `cf5189d`（2026-09-26），外掛版本 1.49.4。
- 官方 README 只寫「Godot 4.x is supported」。它的 CI（自動測試）只在 **Godot 4.2.2** 上跑，從來沒在 4.4 以後的版本測過。

| Godot 版本 | 測試結果 |
|---|---|
| 4.2.2（官方 CI 用的版本） | 333 項全部通過 |
| 4.7.2 | 328 項通過，**5 項失敗**，全部在 `NetworkSchemas`（網路資料壓縮格式） |

查原始碼確認的原因：

- netfox 在 Godot **4.4 以上**改用 16 位元半精度浮點數（只保留較少的小數位）來壓縮資料，4.4 以下則退回 32 位元。CI 只跑 4.2.2，所以 16 位元這條路徑從來沒被測過。
- `vec2f16` 失敗：測試程式第 57 行寫的是 `vec2f32()`，打錯了，所以實際大小 8 bytes 和預期的 4 bytes 對不上。
- `normal2f16`、`quat16f`、`transform2f16` 失敗：測試要求數值完全相等，但 16 位元本來就會損失一些精度，例如 0.866025 變成 0.866106。誤差在合理範圍內。
- 第 5 項是上面幾項的彙總結果。
- 結論：**這是 netfox 測試本身的錯，不是 netfox 在 4.7 上無法運作**。netfox 的 issue tracker 上查不到相關回報。
- 尚未驗證：實際用 netfox 做一個即時對戰範例，在 4.7.2 上跑起來。

### 4. PixiJS 經 Capacitor 在中低階 Android 上的效能　❓ 查無公開的對照數據

本項沒有實機可測，只做了文獻查證（由 subagent 協助，搜尋結果僅看摘要，未逐頁驗證）：

- **找不到** PixiJS v8 經 Capacitor／WebView 執行，與 Godot 原生 App 在同一支低階手機上的對照數據。
- PixiJS 官方的 bunnymark 測試（10 萬個圖片同時移動）：CPU 時間從 v7 約 50ms 降到 v8 約 15ms。但官方沒寫測試裝置，推測是桌機。（官方部落格）
- WebGPU 支援：
  - Android 版 Chrome 121 起，在 Android 12 以上且使用 Qualcomm 或 ARM 顯示晶片的手機上預設開啟。（Chrome 官方）
  - 但 **Android System WebView（App 內嵌的瀏覽器元件）是否同步開啟，沒有查證到**。
  - iOS 26 的 Safari 預設開啟 WebGPU；WKWebView（iOS App 內嵌的瀏覽器元件）能不能用，Apple 沒有正式說明。
- 已知風險：Android WebView 的 WebGL 畫面資源可能被系統收回（context loss）。曾有一次事故影響約 30 萬名巴西、墨西哥使用者。程式必須能處理 `webglcontextlost` 和 `webglcontextrestored` 事件，重建畫面資源。（Chromium 郵件群組）
- Godot 這邊：官方建議舊款手機使用 Compatibility 繪圖模式。論壇上有個案回報 2D 遊戲移植到 Android 後 FPS 從 60 掉到 22。這只是個案，不是系統化測試。
- **結論**：唯一可靠的方法是在目標的最低階機型上，同時跑 bunnymark 和實際遊戲場景，兩個方案都測。

**套用方式**：

- 原樣複製到 `demos/pixi-colyseus-card/.claude/skills/`，並在 `.claude/VENDORED-SKILLS.md` 記錄來源的 commit 編號、授權和更新步驟。
- 依照官方 Colyseus 技能，把範例改成 0.18 推薦的寫法：
  - `getStateCallbacks` 改成 `Callbacks.get`
  - `this.onMessage` 改成 `messages = {...}`
  - `InstanceType` 改成 `SchemaType`
- 改完後，開發版連跑 3 次、正式版 1 次，**每次 21 項全部通過**。

**發現的不一致**：Colyseus 官方技能說 `getStateCallbacks` 已經移除，但 `@colyseus/sdk` 0.18.5 仍然匯出它，型別定義裡也沒有標註淘汰；同時，`Callbacks.get` 被註明是「新的標準 API」。所以結論是：兩種寫法都能用，新程式碼統一用 `Callbacks.get`。這個衝突已寫進 AGENTS.md。

**啟用驗證**：在範例目錄開一個全新的 `claude -p`（Claude Code 2.1.292，Sonnet），請它寫 Colyseus 程式，但不指定用哪種寫法。結果：

- 它**自己載入了 `colyseus` 技能**，寫出 `callbacks.listen(...)` 和 `messages` 的新寫法。
- 它也遵守了 AGENTS.md 的規則：檢查遊戲階段、拒絕時記錄 REJECT、提醒要補 e2e 測試。
- 遇到規則沒有定義的部分（棄牌後怎麼計分），它停下來詢問，沒有自行決定。
