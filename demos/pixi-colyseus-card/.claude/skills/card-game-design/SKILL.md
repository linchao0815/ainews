# 線上卡牌遊戲設計（伺服器權威 + PixiJS）

原始來源都假設「前端就是權威」，也就是在單機或主機上決定遊戲結果。本專案剛好相反：**結果一律由伺服器決定**。凡是兩者衝突的地方，以本文件為準。API 用法請看各自的技能：`colyseus`、`pixi-addons`、`xstate-flow`、`gsap-core`。

## 1. 牌與牌區（伺服器）

- **每張牌在任何時刻只能存在於一個牌區**，例如牌堆、手牌、場上、棄牌堆。移動一張牌時，要先從原本的牌區移除，再加入新的牌區。移動完成後，用斷言（assert）檢查沒有任何一張牌重複出現。所有牌區的變動，只能寫在 `server/CardRoom.ts`。
- **牌是資料**：一張牌只是 `{ rank, suit, ... }` 這樣的資料，效果寫成資料清單，不要替每張牌各寫一個函式。在 schema 裡只放前端真正需要的欄位。
- **洗牌用 Fisher-Yates 演算法，或其他等價的無偏差抽法**（例如每次從剩下的牌裡隨機抽一張，也就是現在的 `deck.splice(random)`）。**亂數只在伺服器端產生**。需要重播或稽核時，改用可以設定種子（seed）的亂數產生器，並把種子記進伺服器日誌。
- **出牌要一次完成**：先驗證整個動作是否合法，例如現在的遊戲階段、送訊息的人、這張牌是不是他的。全部合法才修改 state；只要有一項不合法，就 REJECT 並記錄，state 完全不動。

## 2. 隱藏資訊與揭曉

- **對手看不到的資料，就不要送到對手的瀏覽器。** 手牌、牌堆順序、下一張牌，都要用 `.view()` 加上 `StateView` 過濾。只在畫面上把牌蓋起來是不夠的，因為瀏覽器拿得到的資料，玩家打開開發者工具就看得到。
- **揭曉要由伺服器把資料公開**：伺服器把牌值複製到公開欄位（本專案用的是 `shownCard`），並在同一次更新裡設定 `phase = "revealed"`。前端只要偵測到 phase 變了，就開始播揭曉動畫。
- **雙方同時揭曉**：兩邊都準備好之後，伺服器在同一次更新裡公開雙方的牌，避免先拿到結果的一方佔便宜。
- **平手規則要寫清楚**：本專案的規則是平手不計分，`winner = "draw"`。新增規則時，要列出所有可能的結果，包括平手、有人斷線、超過時間沒動作，每一種都要有對應的處理，而且要有 e2e 測試。
- **動畫不能決定結果**：動畫只是把伺服器已經決定好的結果演出來。動畫還沒播完時，伺服器的 state 已經是最終結果了。

## 3. 手感回饋（翻牌、勝負）

- **疊加多個小回饋**：重要的瞬間，在大約 100 毫秒內同時觸發好幾個小反應，例如翻牌的縮放動畫、音效、短暫的光暈或粒子效果。
- **依重要程度分三級**，強度要跟著事件的重要性：

  | 等級 | 事件 | 回饋 |
  |---|---|---|
  | 小 | 按下按鈕、滑過按鈕 | 按鈕狀態圖切換、短音效 |
  | 中 | 翻開自己的牌 | 翻牌動畫（0.3 秒）加翻牌音效 |
  | 大 | 揭曉勝負 | 翻開對手的牌、勝負文字彈出、Spine 角色動作、勝利音效 |

- **緩動曲線對照（GSAP 寫法）**：
  - 彈出效果：`back.out`，帶一點過衝。
  - 落定、收尾：`power2.out`。
  - 先收再放（翻牌前半段）：`power1.in`。
- **回饋要短，結束後回到靜止狀態**：回饋不能擋住玩家下一步操作。需要等待的地方，靠狀態機和按鈕的停用狀態處理，不要靠動畫時間來擋。
- **尊重系統的「減少動態效果」設定**：偵測 `matchMedia("(prefers-reduced-motion: reduce)")`。開啟時，翻牌直接換成最後的牌面，不播放縮放、震動、閃光（參考 `CardView.show()` 裡的 `reducedMotion` 分支）。結果和狀態必須完全一樣，只是少了動作。
- 每一段動畫都要可以跳過，也不能卡住遊戲流程。

## 4. 手機 UI（PixiJS + Capacitor）

- **觸控目標至少 44×44 CSS 像素**（iOS 建議 44pt、Android 建議 48dp，大約 9～12 mm）。按鈕之間至少留 8px 的間距。注意 canvas 會被縮放，要算的是**縮放之後**實際顯示的大小。
- **安全區**：瀏海和圓角的位置用 `env(safe-area-inset-*)` 取得，或用 Capacitor 的對應功能（見 `capacitor-app-development` 技能的 safe-area 參考文件）。重要的按鈕和文字不要放在安全區以外。
- **UI 不保存遊戲狀態，也不修改遊戲狀態**：畫面只根據 Colyseus 的 state 和 xstate 的快照重新繪製（本專案的寫法是 `render()`）。UI 物件上不放分數、手牌之類的資料。
- **不要只靠顏色表達狀態**：勝負、能不能按，除了顏色，還要用文字或圖示表示。
- **字串集中管理**：畫面上的文字集中放在一個對照表（參考 `status.text` 那張表），為之後的多語系做準備。按鈕寬度不要寫死成剛好放得下中文，德文之類的語言可能長出約 30%。

## 5. 音效（@pixi/sound，手機版）

- **手機瀏覽器要先有使用者操作，才能播放聲音**：第一次播放要放在玩家點擊之後。iOS 的靜音開關、App 切到背景，都要確認不會讓音效系統壞掉。
- **分組**：音樂、音效、UI 聲音分開管理，每一組的音量可以分別調整。
- **音量滑桿要做對數換算**：人耳對音量的感受是對數的，滑桿的線性數值要換算後再套用，不然調整起來會覺得不均勻。
- **重複的音效要加一點變化**：例如每次播放時，把 `speed` 隨機調整 ±6% 左右，讓連續播放時不會聽起來很機械。
- 只播一次的音效，播完要釋放，或用物件池重複使用。音量要留一些餘裕，避免多個聲音疊在一起時破音。

## 完成條件

- 新增或修改的規則，**每一種結果（贏、輸、平手、斷線、逾時）都有對應的 e2e `check(...)`**。
- 如果是在修 bug：**先寫出能重現 bug 的測試，親眼看它失敗，再修 bug，最後看它通過**。
- `npm run test:e2e` 印出 `ALL PASS`；改動影響畫面時，看過 `logs/e2e/*.png` 截圖。
