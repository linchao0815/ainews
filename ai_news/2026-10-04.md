## 1. **主推工具動態／資安｜Claude Code連發v2.1.288、v2.1.289：新增teammates用「agent.spawn」協作原語，同時修補symlink繞過檔案讀取權限的安全漏洞**
   **新聞內容**：Anthropic於10月2日發布Claude Code v2.1.288、10月3日再發布v2.1.289，延續10月1日「Claude Mods」外掛架構上線後的密集迭代。v2.1.288新增`$.ui.selection()`讓Mod能讀取全螢幕模式下使用者選取的文字、Ctrl+C中斷後可復原被清除的提示、`/code-review`新增`--max-findings`可設定回報問題數上限，並修復「prompt過長」原本會直接讓整輪對話失敗、現在會自動觸發壓縮接續的問題；v2.1.289則修復了一個具體安全漏洞——先前版本中，Read工具的deny（拒絕存取）規則對透過symlink（符號連結）存取的@-mention檔案會失效，形同讓受限檔案可被繞道讀取，本次已修補；同時新增`agent.spawn`供teammates（多agent協作）模式使用，並改進`$.agent.list()`回報agent狀態的準確度，另修復mod清單/更新顯示本機舊快取、以及mod安裝後重啟不會載入的問題。
   **為什麼對我們有意義**：symlink繞過Read deny規則是實質的資安修補——如果公司已經用settings.json限制Claude Code不能讀取某些目錄（例如玩家個資庫、金流設定檔），先前版本理論上可能被symlink技巧繞過，升級後才真正補上這個破口，資安窗口應視為優先修補項目；`agent.spawn`與teammates協作原語則讓多個並行agent之間能有更結構化的溝通介面，對已經在用Claude Code跑多工並行開發（如同時處理美術管線腳本、玩法邏輯、建置流程）的工程團隊，是比先前陽春的sub-agent機制更穩定的協作基礎。
   **建議後續**：資安／IT窗口本週內將所有開發機與CI runner的Claude Code統一升級至v2.1.289以上，並確認settings.json中既有的deny規則在升級後對symlink路徑仍然有效；工程主管則可安排1名重度多agent使用者試用`agent.spawn`／teammates模式，評估是否比現行的ad hoc多視窗工作方式更好管理。
   **來源：**GitHub Release v2.1.288（https://github.com/anthropics/claude-code/releases/tag/v2.1.288）；GitHub Release v2.1.289（https://github.com/anthropics/claude-code/releases/tag/v2.1.289）

## 6. **工具能力（程式，頻道分享）｜Codex CLI的subagent其實預設關閉：開發者實測＋自建profile才能讓平行作業真正穩定運作**
   **新聞內容**（頻道分享）：同事於Telegram頻道「AI收集」分享的Threads貼文指出，OpenAI Codex CLI的subagent（子任務平行處理）功能預設是關閉的，必須手動開啟feature flag才會真正平行執行；即使開啟後，Codex對「哪些任務該拆分、哪些不該拆」的判斷也偏保守，常常呼叫了subagent卻又退回單線執行。貼文作者因此自行寫了一組custom agent profile，開源在GitHub上，並表示唯有如此平行運算才能穩定發揮，讓Codex的實際產出速度有機會追上Claude Code。經查證，OpenAI官方文件與多個技術部落格證實：Codex的`features.multi_agent`確實被標示為實驗性功能、預設關閉，須透過互動式`/experimental`選單或config.toml手動啟用，且可設定`max_threads`（預設6）控制平行子agent數量，與貼文描述吻合。
   **為什麼對我們有意義**：若工程團隊有評估或已在用Codex CLI作為Claude Code以外的輔助選項，這則資訊直接點出一個容易被忽略的「開箱即用」陷阱——沒注意到subagent預設關閉，可能誤以為Codex平行處理能力不如預期，進而低估其實際效能；而這類需要自行寫custom profile才能穩定運作的狀況，也提醒我們在工具選型評估時，不能只看官方宣稱的功能表，還要實際測試功能在預設設定下是否真的如期運作。
   **建議後續**：有評估Codex CLI的工程師，在下次測試時先確認是否已啟用`features.multi_agent`與調整`max_threads`設定，並參考開源的custom agent profile做法，評估自建任務拆分規則是否能改善其平行處理的穩定度。
   **來源：**Threads／Arum Wu（https://www.threads.com/@arumwu/post/DeA85RhE2RD）；GitHub（https://github.com/arumwu/arum-codex-subagents）；OpenAI官方文件（https://developers.openai.com/codex/subagents）

## 7. **成本情報（頻道分享）｜「幫快取續命」技巧在開發者圈流傳：Claude Code 50分鐘前Ping一下避免快取到期，但僅對按量計費帳號有效**
   **新聞內容**（頻道分享）：同事分享的Threads貼文提到一個用Claude Mods實作的省錢技巧——Claude的prompt cache（提示詞快取）預設在閒置一段時間後會過期，過期後下一輪對話就必須重新寫入快取、成本較高；因此有開發者寫了一個Mod，在接近過期前自動Ping一下對話讓快取「續命」，藉此避免頻繁重建快取的額外費用。經查證Anthropic官方文件：預設快取生命週期為5分鐘，可透過`ttl: "1h"`參數延長為1小時，但延長快取的寫入成本是基礎輸入token價格的2倍（5分鐘快取寫入為1.25倍），讀取快取命中則只需基礎價格的0.1倍；GitHub／外掛市集上也已出現多款同類型的「cache-keepalive」Mod與技能（如cache-money、cache-keepalive-plugins），顯示這是開發者社群中具體可操作、而非單一人臆測的技巧。但官方文件與社群討論同時強調一個重要前提：此技巧只對「按token計費」的API帳號有效益；若公司是用Claude Pro／Max／Enterprise這類「依席位計價」的訂閱方案，持續Ping快取反而會額外消耗請求配額，效果適得其反。
   **為什麼對我們有意義**：若工程團隊是透過Anthropic API按token計費的方式使用Claude（例如串接CI/CD自動化流程、或走Claude Managed Agents API），這個技巧能在長時間掛著跑、中間有多次暫停等待（如等人工審核、等外部服務回應）的agent任務中，實質降低快取重建的額外費用；但如果公司主要是員工日常用Claude Code／Claude.ai的Pro或Max訂閱席位，貿然套用這類Mod反而可能浪費訂閱配額，工程主管需要先確認清楚公司各團隊實際是用哪種計費模式，才能判斷是否該啟用。
   **建議後續**：工程主管盤點公司內部哪些Claude串接是走API按量計費（如CI/CD自動化腳本），哪些是走訂閱席位（員工日常互動式使用），只在前者的長時間、間歇性任務場景試裝cache-keepalive類Mod並實測帳單差異，訂閱席位類使用情境則不建議套用。
   **來源：**Threads／Henry Hung（https://www.threads.com/@henrywthung/post/DeCSLBQmmCb）；Anthropic官方文件（https://code.claude.com/docs/en/prompt-caching）；Claude外掛市集（https://www.claudepluginhub.com/plugins/yujiachen-y-cache-keepalive-plugins-cache-keepalive）

## 8. **工具能力（程式，頻道分享）｜Threads流傳Opus 5.5長任務實戰心法：講清楚終點、CLAUDE.md設停止規則、長任務開TASKS.md防失憶**
   **新聞內容**（頻道分享）：同事分享的Threads貼文整理了一套Opus 5.5長任務操作心法，核心是「講清楚終點在哪，然後放手」——例如不要只說「幫我改API」，而要具體描述「每個endpoint都換成新client、舊的刪掉、測試全部通過」，因為Opus 5.5可以自己連續跑好幾個小時，使用者越頻繁插手，反而越難讓它自然收尾。貼文並整理出幾項具體做法：不需要再特別要求「一步一步想」，因為模型本就會在回覆前思考，多要求反而拖慢速度；設計類需求要列出「不要什麼」（例如不要米色背景、不要斜體強調字）通常比籠統說「不要太普通」更有效；在CLAUDE.md中明訂「只有卡住、或要刪資料／強制push時才停下來問」的停止規則；長任務另開一個TASKS.md，即使對話被壓縮摘要也不會忘記進度；大型遷移任務則可呼叫subagent平行處理，最後彙整成一張表。貼文也提到「有測試者反映Opus 5.5開最低effort抓到的bug比Opus 5開高effort還多、誤報還更少」，但這僅是單一使用者的非正式測試心得，並非官方或可驗證的基準數據。
   **為什麼對我們有意義**：這些做法與9/28已報導的Thariq Shihipar「effort怎麼花」官方分析互補——後者說明effort檔位如何影響產出完整度，這篇則補上「如何描述需求、如何設計CLAUDE.md停止規則」的實戰細節，兩者合在一起對工程團隊設計內部Claude Code使用SOP有直接參考價值，尤其TASKS.md防止長任務因上下文壓縮而失憶的做法，直接對應我們在跑大型重構或遷移任務時常見的「agent中途忘記目標」痛點；但關於effort與bug抓取率的具體說法屬於未經驗證的個人心得，不應直接當作效能基準採信。
   **建議後續**：工程主管可將「終點導向描述＋CLAUDE.md停止規則＋長任務TASKS.md」這套做法整理進內部Claude Code使用守則草案，在下次內部技術分享會上搭配9/28已介紹的effort使用心法一併說明；對於「低effort抓更多bug」的說法，建議安排實際對照測試後再決定是否採信，不要直接當真。
